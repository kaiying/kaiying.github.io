FFLogs 對帳流程 ​

這套流程用同一份 ACT log 比較本專案與 FFLogs 的結果。第一版先建立離線案例格式與全玩家摘要比較；FFLogs API 匯入器完成後，會自動產生 baseline，不需要人工抄寫玩家數字。

rDPS、連環計與 Crit / Direct Hit buff 的公式跟進計畫見 doc/fflogs-rdps-validation-plan.md。

使用者要填的資料 ​

編輯 fflogs/cases.json：

json
{
  "schemaVersion": 1,
  "cases": [
    {
      "url": "https://www.fflogs.com/reports/REPORT_CODE#fight=12&type=damage-done",
      "logFile": "logs/Network_30200_20260528.log"
    }
  ]
}

必要欄位只有：

  • url：FFLogs report URL，最好已選定 fight。
  • logFile：同一份紀錄在 workspace 內的路徑。

只需要填這兩欄。不要把 FFLogs client secret 寫進這個檔案。

檢查案例設定 ​

bash
npm run compare:fflogs

FFLogs baseline 尚未匯入時，命令會：

  1. 驗證 URL 並解析 report code / fight。
  2. 確認 ACT log 存在。
  3. 從 public/data/pulls-index.json 找到該 log 的 generated report。
  4. 列出所有本機 pull，等待後續用 FFLogs fight 時間自動配對。

如果 generated report 不存在，先執行：

bash
npm run parse

Baseline 與全玩家比較 ​

FFLogs 匯入流程之後會依 URL 自動在 fflogs/baselines/ 產生 baseline。這是工具管理的資料，不需要使用者建立、指定檔名或填寫。

比較器預設檢查整個 fight 與 baseline 內的所有玩家。目前支援：

  • fight duration、kill / wipe
  • 全隊總傷害、治療、承傷
  • 每位玩家的 job、damage、DPS、healing、HPS、casts、deaths
  • 每位玩家選填的 FFLogs rdps、buffGiven、buffTaken、buffNet；分別比較本機 estimatedRdps 與 raidBuffGiven/Taken/Net
  • 每位玩家選填的 critRate、directRate、critDirectRate
  • 頂層選填的 raidBuffContributions，可比較玩家的 damage、Buff Given/Taken/Net、estimated rDPS 與 attributed event count

只有 baseline 實際包含的欄位才會比較，因此未提供 Buff Given/Taken 或 Crit/DH 的案例仍可直接使用。容忍誤差為 duration 0.1s、DPS/HPS/rDPS 0.1、傷害／治療／Buff contribution amount 1、rate 0.1 個百分點；casts、deaths 與 attributed event count 必須一致。超出容忍誤差的數值保留在分類明細；exit code 的意義見下節，不能把現有已知差異一概當成新回歸。

如果 FFLogs fight 無法自動配對本機 pull，工具會列出候選項目，再處理例外情況；正常使用仍只需 URL 與 log 檔名。

比較分類與工具契約（2026-09-10） ​

comparePullWithFflogsDetailed 回傳每個已定義比較欄位的明細，包括 scope、metric、local、fflogs、status、reason，以及可比較時的精確 localValue、expectedValue、difference、tolerance。CLI 逐項輸出並彙總分類：

status意義
not-compared（未比較）baseline 未提供，或 local 缺欄／缺列；reason 區分原因，不以零補缺值
passed（通過）兩側有效數值或文字完全一致；合法 0 仍會比較
within-tolerance（允許誤差）非零差但在原有 tolerance 內，不調寬門檻
known-limitation（已知限制）超過 tolerance，但符合具體已稽查案例；保留原值、差額與證據原因
unsupported（尚未支援）baseline 有值，但本地無等價口徑，例如含 mitigation 的預設 Healing／rHPS／過治率
unresolved（未解差異）超過 tolerance 或文字不同，尚無足夠證據分類

非法資料不放入上述六類，直接拋出含欄位路徑的錯誤，由 CLI 計入 invalid。baseline 的根結構、source、fight、列陣列、必填姓名、重複姓名、未知欄位與數值型別都有 runtime validation。CLI 保留 healingView 檢查，直接使用 library API 比較治療時也必須明示未含 mitigation 的 healingView。FFLogs 數字只接受有限 number；null、數字字串、布林值、NaN、Infinity 都不可當成零或略過。local 的缺失值不作通過；非有限值或非法型別也報錯。

未提供的 baseline 選填欄位可繼續省略，會顯示未比較；不存在的 local 指標列即使對照值為零也不宣稱一致。空 metric array 的全隊合計仍為合法零；個人列缺失與個人明確提供零值則分開處理。過治率若缺 raw／absorbs／overheal 任一 local 值，標成未比較。

唯一內建的已知限制規則是 XDt7a138MhLqNbkx / last、Network_30207_20260811.log、local pull 14、草灰妲 absorbs 的精確 3,002,285 對 3,084,675，差 -82,390。證據是三筆完全吸收事件 32,350 + 3,897 + 46,143，見 治療稽查紀錄。任一來源或數值改變就回到未解差異；F34、rDPS 與其他治療差異沒有整批白名單。

相容 API comparePullWithFflogs 仍回傳陣列並保留舊欄位；既有正常案例及 tolerance 行為維持。陣列現在也包含缺 local、尚未支援等需注意項目；需要完整 coverage 或分類時改用 Detailed API，勿再以陣列為空當成所有資料均已驗證。儲存 report schema 與正式 parser 公式沒有改變，parserVersion 維持 57。

CLI exit code ​

兩個 comparator 共用以下規則，優先順序為 2 → 1 → 3 → 0：

code意義
0至少有一項可比較檢查，全部為通過／允許誤差／已知限制；無缺 local 或尚未支援的預期欄位
1有未解差異；表示需追查，不自行宣稱是新回歸
2非法 baseline／local／設定或讀檔錯誤
3不完整：缺 baseline、未設定案例、沒有可比較指標、缺 local，或仍有尚未支援欄位

省略 baseline 選填欄位本身不阻擋其他有效檢查的 exit 0；完全沒有可比較欄位則 exit 3。compared 是成功產生明細的案例數，不是通過數；differences 只計未解差異與已知限制，其他狀態見分類合計。設定檔／JSON 在案例迴圈前就無效時，直接報錯 exit 2。

可重跑驗證 ​

bash
npx vue-tsc --noEmit
npm test -- --cache=false
npm run docs:build
node --import tsx src/parser/tools/compareFflogs.ts

node --import tsx 與 npm script 執行相同入口，可避免受限環境中 tsx CLI 的 socket EPERM。需使用支援 --import 的 Node 版本；本次使用 Node 24。

本次唯讀使用主工作目錄的既有 generated data 與 baseline，沒有重新 parse。FFLogs compared=1, differences=82, invalid=0，分類為未比較 71、通過 17、允許誤差 0、已知限制 1、尚未支援 41、未解差異 81，exit 1。先前 84 項數值差異中，高岳霆與 Y韭的 overhealPercent 因缺 local absorbs 列改為未比較；兩人的 absorbs 原先以零通過，也改為未比較。四項都保留原因，沒有填補數值或宣稱準確度提升。其餘未提供 baseline 欄位共 67 項。
