FFLogs 數據驗證與 rDPS 跟進計畫 ​

Status: Partial

目標：讓本機 analyzer 可以逐步接近 FFLogs 的可驗證口徑。短期維持 rDPS* 標示；只有在對帳案例穩定通過後，才考慮調整 UI 文案。

原則 ​

  • 以同一份 ACT log 對同一個 FFLogs fight 做對帳，不用不同場次或人工目測判斷。
  • 先做可重跑的 baseline compare，再調整公式。
  • 每個會影響輸出的公式改動都要 bump parserVersion，並重新 npm run parse。
  • 對帳未通過前，UI 保持 rDPS* 與低/中信心標示。
  • 連環計屬於目標 debuff，不是玩家身上的 party buff；rDPS attribution 必須支援這種套用方向。

現況 ​

已完成：

  • npm run validate:data：檢查 generated pull / timeline 的內部加總一致性。
  • npm run compare:fflogs：已有 FFLogs 對帳殼，可以讀 fflogs/cases.json 與 fflogs/baselines/。
  • 已有 1 個可重跑的 healing baseline：XDt7a138MhLqNbkx / fight=last 對本機 pull 14；parserVersion 51 regenerated data 重跑為 compared=1, differences=59, invalid=0。
  • 技能軸 M2：timeline JSON 已輸出 raw player action 對技能軸可視事件的 castReconciliation。
  • Raid buff metadata 已收錄第一批：占卜、戰鬥連禱、連環計、技巧舞步結束、灼熱之光、鼓勵、義結金蘭：攻擊。

主要缺口：

  • 現有 1 個案例只含 healing／absorbs 欄位，尚不能驗證 rDPS*、Buff Given/Taken 或 Crit/DH attribution。
  • FFLogs baseline schema 尚未納入 rDPS、buffGiven、buffTaken、critRate、directRate。
  • 倍率型 buff 分攤目前用線性權重，FFLogs 使用 log-weight。
  • Crit / Direct Hit buff 目前用固定期望倍率，FFLogs 使用事件 crit/DH portion 與玩家 unbuffed/buffed crit/DH 機率。
  • 連環計是套在敵人的 debuff；目前 rDPS matching 主要用「buff target 是傷害來源玩家」的模型，需支援 target debuff。
  • DoT tick 已有 snapshot offset，但還沒有明確 direct / dot event kind，無法套 FFLogs 的 DoT crit/DH 公式。

M2. 倍率型 Buff 改成 FFLogs Log-Weight ​

Status: Planned

目標：先讓占卜、技巧舞步結束、灼熱之光、鼓勵、義結金蘭這類倍率 buff 的分攤方式接近 FFLogs。

目前策略：

text
extra = actual - actual / totalMultiplier
share_i = extra * ((m_i - 1) / sum(m_i - 1))

目標策略：

text
M = product(m_i)
lost = actual - actual / M
share_i = lost * (log(m_i) / log(M))
  • [ ] 將 splitEstimatedExtraDamage() 改成 log-weight。
  • [ ] 保留單元測試案例：
    • 單一 10% buff。
    • 兩個 10% buff。
    • 5% + 6% buff。
  • [ ] 更新 doc/formulas-qa.md 與 doc/fflogs-formula-reference.md 的本機公式。
  • [ ] bump parserVersion。

驗收：

  • 單一 buff 的結果不變。
  • 多 buff 疊加時，分攤符合 FFLogs help 的 log-weight 公式。
  • npm run validate:data 通過。

M3. 支援 Target Debuff 型 Raid Buff ​

Status: Planned

目標：讓連環計這類「套在敵人身上、讓打該敵人的玩家受益」的 buff 能被 rDPS attribution 捕捉。

  • [ ] 擴充 BuffMetadata：
    • application: 'sourceBuff' | 'targetDebuff'
  • [ ] 現有 party buff metadata 標成 sourceBuff。
  • [ ] 連環計標成 targetDebuff。
  • [ ] rDPS matching 改為依 application 判斷：
    • sourceBuff: buff.targetId === damage.sourceId
    • targetDebuff: buff.targetId === damage.targetId
  • [ ] Raid buff contribution table 顯示模型仍可沿用，但 tooltip 要說明 target debuff 已納入。
  • [ ] bump parserVersion。

驗收：

  • 含學者的本機 log 中，連環計期間打同一目標的隊友傷害會被列入 attributed events。
  • 沒有學者或沒有連環計 status 的 pull，不應新增連環計 contribution。
  • npm run validate:data 通過。

M4. Crit / Direct Hit Buff 公式第一版 ​

Status: Planned

目標：取代目前固定期望倍率，讓連環計 / 戰鬥連禱開始接近 FFLogs 的 crit buff attribution。

FFLogs 口徑摘要：

  • 倍率 buff 先從實際傷害中取走 percentage buff 的 share。
  • Crit / DH buff 再對剩餘傷害 N' 計算 crit portion / direct hit portion。
  • 一般直接傷害依事件是否 crit / direct hit 計算。
  • DoT tick 使用 simulated tick 公式，不能和一般直接傷害共用同一套。

第一版本機策略：

  • [ ] 從本場觀測資料估算每位玩家的 unbuffed crit rate / direct rate。
  • [ ] 將 active critRateBonus / directRateBonus 納入 buffed rate。
  • [ ] 對直接傷害事件：
    • 非 crit 事件不分配 crit buff 貢獻。
    • crit 事件依 FFLogs help 的 crit portion 公式分配。
    • direct hit 同理。
  • [ ] 對 DoT tick：
    • 先標成 low confidence。
    • 若缺少足夠資料，維持保守估算或暫不分配，不能混成 direct event。
  • [ ] 將 RaidBuffAttributionModel 擴充成可區分 critDirectFormula。
  • [ ] bump parserVersion。

驗收：

  • 連環計不再以固定 1.05 近似處理。
  • rDPS* 信心仍標示為 low，直到 FFLogs baseline 差距穩定。
  • 有連環計的案例可在 compare:fflogs 看出差距縮小。

  1. M1：先讓 FFLogs compare 能比 rDPS 相關欄位。
  2. M2：倍率 buff 改 log-weight，風險低、收益明確。
  3. M3：支援 target debuff，讓連環計真正進入 attribution。
  4. M6：補至少一份含連環計的對照案例。

  6. M5：補 DoT event kind 與 simulated tick 分支。
  7. M7：把驗證固定化。

暫不做 ​

  • 不串 FFLogs 帳號 OAuth，不要求使用者註冊或公開資料。
  • 不做全站 percentile / parse rank。
  • 不把 rDPS* 改名成正式 rDPS，直到 FFLogs 對帳案例穩定通過。
