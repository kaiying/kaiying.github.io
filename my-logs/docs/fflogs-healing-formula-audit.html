FFLogs 治療公式稽核 ​

對帳場次：XDt7a138MhLqNbkx / fight=last / options=0

這份文件先固定「公式與事件處理順序」，不以總量差值反推倍率。數值權威表仍在 doc/fflogs-XDt7a138MhLqNbkx-fight-last-baseline.md。

證據等級 ​

  • 公開定義：FFLogs 官方文件明確說明。
  • 本場驗證：可由 FFLogs 表格／事件頁與同一份 ACT network log 逐筆驗算。
  • 尚未公開：FFLogs 沒有公開 FFXIV parser 的完整實作；只能繼續用逐事件對照確認，不能假裝已知。

官方參考：

  • FFLogs filter/event fields：https://www.fflogs.com/help/pins
  • FFLogs uploader release notes：https://www.fflogs.com/client/release-notes/
  • rDPS 的 given/taken 基本形式：https://www.fflogs.com/help/rdps

FFLogs 已確認公式 ​

Healing category ​

公開定義：

text
raw healing event       = 治療原始量（包含 overheal；absorb event 的 raw 等於 absorb）
effective healing event = 治療實際生效量（排除 overheal；包含 absorb）

本場「effective healing + absorbs、mitigation 關閉」子口徑驗證：

text
Amount = effective direct/periodic healing + consumed absorbs
HPS    = Amount / FFLogs fight duration

例如占星：

text
7,275,304 effective heal + 936,850 absorbs = 8,212,154 Amount
8,212,154 / 約 600.33 秒 = 13,679.3 HPS

FFLogs 表尾的 601.1s Total Active 不是 HPS 分母。由八名玩家的 Amount / HPS 交集反推， 本場 HPS 分母介於 600.3322s 與 600.3355s；目前本地 pull 是 601.0s，pull boundary 本身 已有約 0.67s 的差異。

Overheal ​

本場逐列可精確驗證：

text
direct/periodic overheal = raw direct/periodic healing - effective direct/periodic healing
Overheal %               = overheal / (raw direct/periodic healing + consumed absorbs)

例如占星：

text
12,869,223 / (20,144,527 + 936,850) = 61.045...% -> 61.05%

所以 FFLogs 主表的 Overheal% 分母包含實際吸收量；absorb 本身不產生 overheal。

rHPS ​

本場展開列可驗證 FFLogs 使用 given/taken 重新歸因：

text
rHPS = (Amount + healing buff given - healing buff taken) / FFLogs fight duration

對單一 m 倍的受治療增益，事件的增益貢獻為：

text
buff contribution = effective healing - effective healing / m

例如 FFLogs 展開列會顯示鐵壁、戰慄、生命回生法、異想的幻光、放浪神之箭等 Given／Taken。 本地公式的加減方向正確，但目前 metadata 只收錄鐵壁、戰慄、生命回生法，因此本地 rHPS* 不是完整 FFLogs rHPS。多個增益同時存在時，FFLogs 如何分攤 contribution 尚未由公開文件完整說明， 必須逐事件核對，不能用任意權重補齊。

FFLogs 的事件重建規則 ​

直接治療：不是每行獨立 min(raw, missing HP) ​

FFLogs uploader release notes 明確提到：

  • healing 會拆成 calculation event 與實際生效 event；
  • preparation event 會以 packet id 配對；
  • overheal 會被限制在 heal amount 內。

本場陽星同一個 AOE packet 000009DC 可驗證 FFLogs 會整批協調事件，而不是把每個 action line 各自獨立計算：

目標log rawaction HP snapshot單行 min(raw, max-current)FFLogs effectiveFFLogs overheal
高岳霆24,156156,570 / 169,60913,03913,03911,117
草灰妲24,267144,922 / 154,3689,4467,90316,364

第二列相差剛好 1,543，證明 action line 的 HP 欄位雖可當重要輸入，但不足以單獨決定 effective heal； 同 server tick 的其他 healing calculation／resolution 也會參與 HP 預算。本地現改以 action sequence 與目標配對 NetworkActionSync（37），用實際 HP 增量回填 preparation event 的 effective／overheal； Earthly Star、Lady of Crowns、Horoscope、Helios、Essential Dignity 與 Macrocosmos 已在本場逐技能 對到 FFLogs。沒有 packet id 的事件才保留 snapshot frame fallback。

合併 HoT：先拆來源，再算各事件有效量 ​

NetworkDoT 的 HoT / effectId=0 是合併 tick，不代表整包都屬於封包上的 source。

本場黑魔可直接驗證 FFLogs 的週期治療包含：

  • 已知 active HoT（例如陽星合相、活性紋等）；
  • 自然生命再生（FFLogs ability 1302）；
  • 無法單獨辨識時的 Multiple Players Combined HoTs。

黑魔自然生命再生多數事件是 1,543，等於最大 HP 154,368 的 1% 取整；但 05:27.241 只有 286，08:30.253 是 1,276，09:45.250 是 692。 NetworkDoT / effectId=0 的 amount 不含自然生命再生；自然再生由 NetworkUpdateHP（39）行 獨立重建。39 行 current HP 與前一筆 HP cache 的正差是本次實際使用量，再以 floor(max HP × 1%) 封頂；因此滿血溢補不會產生 raw 或 overheal。這個算法逐筆得到上述三個 部分事件，並在本場黑魔精確得到 48 次、71,689，與 FFLogs 相同。

line 24 的 source HP 則是週期效果攜帶的舊快照，不能拿來更新 source 的即時 HP cache。本場占星在 Lady of Crowns 的 NetworkActionSync(37) 已補滿至 154,399 後，45ms 後的他人 HoT line 24 仍帶著舊值 129,080；舊實作因此讓下一筆 line 39 多算 1,543。停止回寫 source HP 後，占星 自然回血為 42 次、64,806，也與 FFLogs 逐筆相同。各技能 HoT 來源的 raw 重建仍需更多逐事件 fixture。

護盾：只有 consumed absorb 進 Amount/HPS ​

公開定義與本場事件頁一致：absorb ability 的 effectiveHealing 就是實際吸收量。

text
shield capacity remaining = generated capacity - cumulative absorbed damage
effective absorb           = 每次 damage event 實際消耗的 shield
未消耗餘盾                 = 0 healing contribution

展開戰術 E01 是特殊的容量複製事件：原始鼓舞的容量由施放目標既有 129 狀態取得，擴散對象只會 收到新的 129 狀態，不會收到新的 heal amount。因此本地在 E01 action 時暫存原盾容量，於後續 26 行 逐目標套用。治療量轉護盾容量按技能倍率計算後必須向下取整；此修正使本場學者 absorbs 由 2,871,855 收斂到 3,087,342；FFLogs 為 3,084,675，差 +2,667（0.086%）。

本場擺脫事件頁會明確列出：

  • absorbs N damage：這個 N 才進 Absorbs/HPS；
  • fades ... (護盾強度: 0)：護盾耗盡；
  • fades ... (護盾強度: 23155)：仍有餘盾，這個餘額不進 Absorbs/HPS。

擺脫容量應逐次施放計算：

text
capacity ratio = 15% + 2% * 本次施放實際消耗的合格防禦效果數（最多三個）
target capacity = 依遊戲／FFLogs 取整規則套用 target max HP

不能一律用 21% 上限。本場第一組完整耗盡事件的數字（例如舞者 25,503、占星 23,159、 絕槍 36,676）均對應各目標最大 HP 的 15% 向下取整，證明至少該次施放不是 21%。本地現已改為 逐次保存 floor(target max HP × 15%) 的基本容量，不再用 21% 上限代替事件證據。

FFLogs 如何在多個可疊加／不可疊加盾同時存在時決定消耗順序，公開文件沒有完整表格；必須從 每筆 absorbs、status apply/remove 及該技能的 stacking 規則核對。僅用 raw damage - HP loss 且只接受單一 active shield，是本地保守估算，不等同 FFLogs parser。

本地目前公式 ​

Direct / periodic effective healing ​

text
direct effective = min(raw, 同 packet id 的 line 37 current HP - 結算前 HP cache)
periodic effective = min(raw, 同一 healing frame 尚未分配的實際 HP 增量)
overheal = raw - effective

直接治療以 action sequence 配對 NetworkActionSync(37)，再按原事件順序分配實際 HP 增量；沒有 packet id 的舊格式才退回 HP snapshot healing frame。週期治療使用 line 24 之前的 target HP cache， 而 line 24 source HP 不回寫 cache。

Merged HoT / natural regen ​

text
1. 對 NetworkDoT amount 執行 effective-heal 估算並分配給 active HoT 候選
2. 同 server frame 的 direct heal 繼續共用 missing-HP 預算
3. NetworkUpdateHP(39) 的自然再生 = min(floor(max HP × 1%), max(0, current HP - previous HP))

多來源 HoT 的 raw 目前仍依 tooltip potency 權重拆分；這部分尚未完整重現 FFLogs 的各來源 calculation event。自然回血獨立來自 39 行，不與合併 HoT 共用或扣減 raw amount。

官方職業指南列出的週期威力為陽星合相 175、河流神之瓶 200；本地已據此修正 F33 權重。FFLogs 在 00:46.160 將同一筆 ACT 合併量 26,455 還原成河流神 12,908 與陽星合相 13,547，兩者 正好守恆，但各自帶獨立隨機浮動，因此只按 potency 比例仍不會逐筆完全相同。 修正後本場河流神 effective 由 33,475 收斂至 46,938（FFLogs 65,145），且團隊 raw/effective 總量不變；這是合併 tick 的來源重分配，不是額外製造治療量。

Absorb ​

text
estimated absorbed = raw damage - observed HP loss

再以 active shield source、已知容量、overkill guard 與同 frame damage guard 歸因。擺脫以 15% 最大 HP 的狀態實例追蹤；原初的血煙（A78）、激勵也已納入 shield status。不同來源多盾同時存在時 多數仍不歸因。這是估算公式，不是 FFLogs 的完整 shield event reconstruction。

HPS* / rHPS* ​

text
local HPS*  = (local effective healing + local estimated consumed shield) / local pull duration
local rHPS* = (local Amount + recorded buff given - recorded buff taken) / local pull duration

本地 HPS* 只對應 FFLogs 未含 mitigation 的子口徑，不等於 FFLogs 預設 Healing HPS；差異還來自 分子事件重建與 fight duration。rHPS* 另有 healing-buff metadata 不完整的差異。FFLogs 預設表 必須取得 calculateddamage 的 mitigated / unmitigatedAmount / packetId 後另行實作，不能由總量 差額推回。

下一步：只做事件規則，不做倍率校正 ​

  1. 以 FFLogs events/CSV 建立直接治療 fixture：保存 packet id、raw、FF effective、FF overheal、 action HP、相鄰 37/38 HP update 與同 tick 其他治療。
  2. 以每個 HoT effectId=0 建立來源拆分 fixture；先求出 FFLogs 每個來源的 raw/effective，才決定 本地的 calculation/resolution 排序。
  3. 繼續補強每次擺脫的強化狀態 fixture；基本 15% 與 consumed/remaining 已逐狀態實例處理，仍須辨識 17/19/21% 的施放。
  4. 以 FFLogs fight window 修正 pull boundary，避免分子正確後仍有 HPS 分母誤差。
  5. 只有 fixture 能逐事件通過後才修改 parser；總量只當回歸驗收，不作為倍率來源。
