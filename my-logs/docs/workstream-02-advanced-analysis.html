工作規格 02：進階分析 ​

文件狀態 ​

  • 編號：02
  • 名稱：進階分析
  • 狀態：規劃完成，等待工作規格 01
  • 目前是否開始實作：否
  • 優先級：第二順位

這份文件定義進階分析的目標、前置條件、工作清單與驗收方式。它不是目前正在執行的工作；在 「工作規格 01：FFLogs 指標對帳」完成前，只保留規劃、資料盤點與不影響主線的研究。

與工作規格 01 的順序 ​

整體開發順序固定如下：

  1. 工作規格 01：FFLogs 指標對帳
    • 先完成 Healing：raw healing、effective healing、overheal、absorbs、HPS、rHPS 與 mitigation 口徑。
    • Healing 穩定後，對帳 DPS 系列：Damage、DPS、nDPS、aDPS、rDPS，以及 Crit／Direct Hit 等相關欄位。
    • 公式必須來自 FFLogs 定義、官方技能資料或可重現的逐事件證據，不用報告專用倍率硬調。
  2. 工作規格 02：進階分析
    • 使用已校準的事件、指標與 metadata，建立死亡回放、成功把比較、團隊技能計畫及操作建議。

工作規格 01 的既有文件：

  • doc/fflogs-reconciliation.md
  • doc/fflogs-healing-formula-audit.md
  • doc/fflogs-rdps-validation-plan.md
  • doc/fflogs-XDt7a138MhLqNbkx-fight-last-baseline.md
  • doc/formulas-qa.md

工作規格 01 目前卡點 ​

目前 Healing 尚未完成，因此 DPS 系列與本規格都不得視為主線已開始：

  • 有效治療仍與 FFLogs 有差距。
  • 建築神之塔的 400 potency 尚未完整重建成實際護盾容量。
  • 部分多盾、同 server frame HP snapshot 與 mitigation 口徑仍待校準。
  • Healing 穩定後，才開始逐欄對帳 Damage、DPS、nDPS、aDPS 與 rDPS。

工作規格 01 的完成門檻 ​

  • [ ] Healing 所有主表欄位都有明確公式與 FFLogs 基準。
  • [ ] 有效治療、overheal、absorbs 的剩餘差異都有逐事件解釋。
  • [ ] DPS 系列各指標已有獨立定義，不混用 Damage、DPS、nDPS、aDPS、rDPS。
  • [ ] 至少建立多場、不同職業組成的 FFLogs regression baseline。
  • [ ] npm run compare:fflogs 能清楚區分已通過、允許誤差與尚未支援的欄位。
  • [ ] 程式、doc/formulas-qa.md、設定文件與 parserVersion 保持一致。

進階分析的產品目標 ​

進階分析要回答的是：

這一把為什麼失敗，與成功把相比差在哪裡，下一把最值得調整什麼？

它不以 FFLogs 排名或模糊總分為目標，也不應只用固定門檻評價玩家。任何結論都必須能回到具體的 log 事件、技能、狀態、時間點與公式。

核心原則 ​

  • FFLogs 對帳結果是指標口徑的第一標準。
  • 使用者指定的成功把是團隊實戰比較的第一基準。
  • 同一玩家、同一 encounter 的歷史 pull 優先於通用門檻。
  • log 直接證據、公式重建與合理推估必須分級顯示。
  • 證據不足時顯示「無法判定」，不產生肯定式建議。
  • 所有建議必須附時間點與來源事件，並可跳回 timeline。
  • 不以單一 overheal、GCD uptime 或 DPS 數字直接判定操作好壞。

第一階段：可信事件與分析證據 ​

  • [ ] 每項分析標示資料來源：log 直接事件／公式重建／合理推估。
  • [ ] 顯示 action、status、potency、owner 等 metadata 覆蓋率。
  • [ ] 建立 Action → Status ID 對應。
  • [ ] 補齊技能類型：傷害、治療、HoT、盾、Buff、Debuff、減傷。
  • [ ] 補齊 GCD／oGCD、冷卻、充能與持續時間。
  • [ ] 校準玩家、寵物、召喚物與地面效果 owner 歸屬。
  • [ ] 完善 DoT snapshot 與合併 tick 歸屬。
  • [ ] 辨識死亡、復活、虛弱與衰弱狀態。
  • [ ] 辨識 Boss 不可選取、過場與有效攻擊目標。
  • [ ] 建立 timeline coverage 與缺漏報告。
  • [ ] 每項建議保存支持它的事件 ID／時間點。

驗收 ​

  • 隨機抽查技能時間軸，施放者、目標、技能與狀態沒有明顯漏記或重複。
  • 使用者能展開任一建議，看到它依據哪些事件及為何成立。
  • metadata 不足的分析會降級或停止，不用預設值假裝精準。

第二階段：死亡回放 ​

  • [ ] 每次死亡擷取前 15 秒事件。
  • [ ] 顯示死亡前 HP 變化。
  • [ ] 顯示受到的傷害、來源與技能。
  • [ ] 顯示收到的有效治療。
  • [ ] 顯示實際使用掉的護盾。
  • [ ] 顯示當時有效的個人／團隊減傷。
  • [ ] 顯示易傷、虛弱及其他危險 Debuff。
  • [ ] 區分單次致死、連續傷害、缺治療、機制失敗與 overkill。
  • [ ] 顯示可能缺少、過早或過晚的防護技能。
  • [ ] 支援成功把相同機制時間點對照。

驗收 ​

死亡卡片能回答：誰在何時被什麼打死、當時有什麼防護、前 15 秒發生什麼，以及哪些內容因資料不足 無法判定。

第三階段：成功把與失敗把比較 ​

  • [ ] 允許指定一把成功紀錄為基準。
  • [ ] 依 Boss 技能、階段或人工錨點對齊兩把時間軸。
  • [ ] 比較相同機制時的 Boss HP 與團隊 HP。
  • [ ] 比較死亡、復活、易傷與失誤 Debuff。
  • [ ] 比較每位玩家 GCD 數與長空窗。
  • [ ] 比較爆發技能與團隊 Buff 漂移。
  • [ ] 比較團隊減傷、護盾與治療技能。
  • [ ] 標示技能早開、晚開、漏開及未覆蓋傷害。
  • [ ] 分離死亡造成的損失與存活期間的操作差異。
  • [ ] 依影響程度列出最重要的差異，不只列全部差異。

驗收 ​

每個失敗 pull 都能產出「相較成功把最重要的差異」，並可跳到兩把對應的時間點核查。

第四階段：團隊減傷與治療計畫 ​

  • [ ] 允許手動建立機制與時間錨點。
  • [ ] 允許為機制配置預定技能與負責玩家。
  • [ ] 支援從成功把建立計畫範本。
  • [ ] 顯示技能是否實際使用。
  • [ ] 計算實際使用相對計畫提早或延後的秒數。
  • [ ] 判斷技能是否實際覆蓋傷害事件。
  • [ ] 顯示同類技能重疊與覆蓋空窗。
  • [ ] 顯示下一個機制前冷卻是否可用。
  • [ ] 顯示當時可用但未使用的技能；證據不足時不下結論。
  • [ ] 依 pull 計算計畫達成狀態，不建立模糊總分。

驗收 ​

每個重要團傷都能顯示計畫、實際使用、覆蓋結果與差異。

第五階段：通用個人操作分析 ​

  • [ ] 找出長 GCD 空窗，排除死亡、過場與 Boss 不可選取時間。
  • [ ] 顯示空窗發生在哪個機制。
  • [ ] 比較主要冷卻技能理論與實際使用次數。
  • [ ] 偵測冷卻技能長時間未使用。
  • [ ] 偵測充能技能溢出。
  • [ ] 顯示兩分鐘爆發漂移。
  • [ ] 顯示 Buff 視窗內的實際技能序列。
  • [ ] 顯示 DoT 中斷與重新施放時間。
  • [ ] 偵測攻擊錯誤目標或無效目標。
  • [ ] 比較成功把與失敗把的個人操作差異。

驗收 ​

建議必須是可行動且可核查的描述，例如「第 242 秒後有 4.8 秒 GCD 空窗」，不能只顯示低於固定分數。

第六階段：職業專屬分析 ​

優先支援團隊實際使用的職業，不要求一次完成全部職業：

  • [ ] 主要資源與量譜。
  • [ ] 連段順序。
  • [ ] 關鍵 Buff 與爆發週期。
  • [ ] 充能、資源上限與溢出。
  • [ ] DoT／HoT 維持規則。
  • [ ] 特殊技能條件與技能變體。
  • [ ] 移動期間可用技能。
  • [ ] 遊戲版本與規則版本。
  • [ ] 每條規則的資料來源與可信度。

驗收 ​

職業建議來自實際職業機制與事件，不再只依賴 GCD uptime 或 Buff action density。

第七階段：Encounter 與機制資料 ​

  • [ ] 建立 encounter metadata 格式與版本。
  • [ ] Boss 技能 ID 與機制名稱。
  • [ ] 階段切換條件。
  • [ ] 團傷、死刑、分攤與連續傷害分類。
  • [ ] Boss 不可選取區間。
  • [ ] Add、物件與有效攻擊目標。
  • [ ] 機制失敗 Debuff。
  • [ ] 擊退、強制移動與站位機制。
  • [ ] 成功、失敗與 wipe 判定。
  • [ ] 允許人工修正及自訂名稱。

驗收 ​

時間軸能以實際機制和階段分段，而不只顯示技能 ID 或大型目標名稱。

第八階段：介面與輸出 ​

  • [ ] 首頁顯示本把最重要的三項發現。
  • [ ] 分成死亡、團隊、個人與資料限制。
  • [ ] 所有建議可跳到時間軸。
  • [ ] 成功把與失敗把可並排比較。
  • [ ] 顯示證據與可信度，不突出模糊總分。
  • [ ] 支援忽略不適用的建議。
  • [ ] 支援團隊註記與人工機制錨點。
  • [ ] 匯出簡潔的檢討摘要。
  • [ ] 保存並重用團隊技能計畫。

最小可用版本 ​

工作規格 02 第一個真正可用的交付，不需要等待所有職業專屬規則完成，但至少包含：

  • 死亡前 15 秒回放。
  • 指定成功把並比較相同機制。
  • 團隊減傷／治療計畫與實際使用比較。
  • 可跳到時間軸的具體建議。
  • 每項結論的證據、公式口徑與可信度。

完成這組功能後，進階分析才從 baseline 統計頁進入可實際協助開荒檢討的階段。

明確不先做的項目 ​

  • 不在 FFLogs 對帳完成前用未校準數字建立職業評分。
  • 不先建立單一「總分」或玩家排名。
  • 不用固定 overheal 門檻直接判定補師操作錯誤。
  • 不用固定 GCD uptime 門檻忽略機制與不可選取時間。
  • 不一次支援所有 encounter 與所有職業。
  • 不把推估值包裝成 log 直接提供的事實。
