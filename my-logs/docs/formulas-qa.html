計算公式說明 ​

這份文件整理本專案所有指標的計算公式、資料來源與已知限制。 想知道「某個數字怎麼算出來的」，先查這裡。

實作位置以 src/parser/ 為準。

傷害公式 ​

DPS ​

DPS = 有效傷害 / 戰鬥秒數
戰鬥秒數 = pull end - pull start

Limit Break 若技能名稱或 ability ID 在 limitBreak.ts 的辨識清單內，會獨立成 Limit Break 傷害列，不掛在施放玩家身上；總傷害仍包含 Limit Break。目前清單只收錄已驗證的 LB（生者必滅 / 1EB5），未收錄的 LB 會被歸到施放玩家的 DPS。

實作：report/metrics.ts 的 toActorMetrics。

有效傷害（overkill 排除） ​

對齊 FFLogs 的 effective damage 口徑：

有效傷害 = min(原始傷害, 目標當下剩餘 HP)

超過目標剩餘血量的部分（overkill，殺敵瞬間的溢出傷害）不計入。 目標 HP 來自 log line 的 HP 快照（action line 為 fields[24]/[25]、DoT tick 為 fields[7]/[8]，即被 tick 實體的 HP），缺漏時 fallback 到 HP cache。

限制：同一 server frame 的多筆命中共用同一 HP 快照，overkill 是估算而非精確值；快照缺漏或為 0 時不裁切，避免誤刪整筆傷害。

實作：report/accumulator.ts 的 toEffectiveDamage。

rDPS* ​

與 FFLogs 的 rDPS 概念相同、精度不同，所以標了 *：

rDPS* = (個人有效傷害 - 吃到的外部 raid buff 收益 + 自己提供給隊友的 raid buff 收益) / 戰鬥秒數

buff 收益估算：

基準傷害 = 實際傷害 / 所有生效 buff 的總倍率
額外傷害 = 實際傷害 - 基準傷害
多 buff 疊加時，額外傷害依各 buff 的增傷權重 (倍率-1) 拆分給提供者

與 FFLogs 的差距：只收錄已驗證的 raid buff metadata；Crit/DH 類 buff（連環計、戰鬥連禱）用保守期望值常數（每 1% crit rate ≈ 0.5% 增傷、每 1% DH rate ≈ 0.25% 增傷），不是依玩家副屬性與事件 crit/DH portion 精算。連環計 metadata 已收錄，但它是套在敵人身上的 target debuff，目前 target-debuff 型 attribution 仍在 doc/fflogs-rdps-validation-plan.md 的 M3 跟進。

實作：report/rdps.ts 的 estimateRaidBuffContributions。

DoT 的 buff 歸因（snapshot） ​

DoT tick 的 buff 歸因用狀態施加當下（snapshot），不是 tick 發生時間——符合 FFXIV 的 DoT snapshot 機制：

DoT tick 的歸因時間 = 該 DoT 狀態最後一次施加的時間（snapshotOffsetSeconds）
直接傷害的歸因時間 = 事件發生時間

所以在 raid buff 視窗內上的 DoT，buff 結束後的 tick 仍算進 buff 貢獻。

限制：合併 tick（effectId 0）用「同來源、同目標」的作用中狀態回推，可能配到同來源的非 DoT debuff（如牽制），owner 正確但 snapshot 時間可能取到鄰近狀態。

實作：report/accumulator.ts（addTickReportEvent）＋ report/rdps.ts。

Boss / add 傷害分類 ​

沒有 encounter 資料庫，用 HP heuristic：

boss 候選 = 目標最大 HP ≥ max(100,000, 玩家最大 HP × 8)

再依 primary target、BNpc 資訊細分 boss / add / object / pet。分類結果影響 bossDamage / addDamage 等統計，不影響總傷害。

實作：targetClassification.ts、pull/rules.ts 的 isPrimaryTargetCandidate。

Crit / Direct Hit ​

Crit / DH / CDH ​

Crit% = crit hits / hits
DH%   = direct hits / hits
CDH%  = 同時爆擊且直擊的 hits / hits

crit/DH 從 action effect flags 讀取（bit 0x2000 = crit、0x4000 = direct hit）。

限制：DoT tick（line 24）沒有 flags，計入分母但一律視為非爆擊，所以 DoT 重職業的顯示值會比實際爆擊率低。

實作：actionEffect.ts（flags 解析）、report/metrics.ts（比率計算）。

治療公式 ​

網站主治療指標優先採 FFLogs healing category 概念：有效 direct heal 與實際 absorb 都算 healing，overheal 不算 HPS。ACT overlay 的 raw Healed 口徑只保留在對帳工具。

戰鬥摘要 ​

摘要卡片的治療數字來自整場 pull 彙總：

有效治療 = sum(玩家有效治療)
原始治療 = sum(玩家原始治療)
過度治療 = 原始治療 - 有效治療
戰鬥摘要過治% = 過度治療 / 原始治療

實作：pullSummary.ts 的 overhealPercent。

治療表 HPS（目前網站口徑） ​

網站主表的 HPS 欄：

HPS = (有效治療 + 有效護盾(估)) / pull duration seconds

護盾只有在被傷害實際吸收後才算有效；施放後仍剩餘、未被打掉的盾不進 HPS。即 有效治療 欄位的「直接治療 + 已耗盾」除以戰鬥秒數。

網站另顯示 FFLogs 概念的本地估算 rHPS*：

受治療增益額外量 = effective heal - effective heal / 所有外部受治療倍率乘積
rHPS* = (有效治療 + 已耗盾 + 增益提供量 - 外部增益接受量) / pull duration seconds

目前已驗證並納入：鐵壁（15%）、戰慄（20%）、生命回生法（10%）。只重新歸因已發生的有效治療，不把 overheal、未消耗護盾或無法歸屬的 HoT 搬移。全隊增益提供量與接受量守恆，因此團隊 HPS 與團隊 rHPS* 總和相同。星號表示 healing buff metadata 尚未完整，不能宣稱等同 FFLogs rHPS。

目前本地可直接對帳的子口徑是 FFLogs healing 的「effective healing + absorbs、mitigation 關閉」： 包含有效治療與實際吸收，但不含 mitigation。它不是使用者開啟報告 URL 時看到的 FFLogs 預設 Healing 主表；兩者不得共用同一個 Amount / HPS 基準。FFLogs 預設表的 mitigation 必須由逐筆 calculateddamage 事件中的 mitigated、unmitigatedAmount 與 packetId 驗證後再實作，不能用兩張 總表的差額回填。

ACT overlay 對帳工具仍按截圖欄位計算：

Overlay Healed = Eff.Heal + OverHeal + D.Shield
               = 原始治療 + D.Shield

pull duration seconds 是本地偵測的戰鬥秒數，也就是 pull end - pull start。FFLogs 的精確分母應取 該 fight 的 endTime - startTime；目前兩者仍有邊界差異。overlay 對帳工具為了比對截圖，會另外 使用 active damage duration；那又是另一個口徑。

治療表欄位 ​

有效直接治療 = min(原始治療量,
                    同 packet id 的 NetworkActionSync(37) current HP - 結算前 HP cache current HP)
有效治療（主表） = 有效直接治療 + 已被傷害消耗的有效護盾(估)
原始治療 = heal / HoT effect 的 raw amount
過度治療 = 原始治療 - 有效治療
治療表過治% = 過度治療 / (原始治療 + 已耗盾)

NetworkAbility / NetworkAOEAbility（21/22）是 calculation/preparation，不是治療已實際生效的時間點。 直接治療先依 action packet sequence 與目標暫存 raw amount；收到相同 packet id 的 NetworkActionSync（37）後，才以前後 HP 實際增量依原事件順序分配 effective，剩餘為 overheal。 無 packet id 的舊格式才退回 HP snapshot healing frame 估算。

NetworkDoT 的 HoT effectId=0 是技能 HoT 的合併 tick，不可把封包 source 或任意 active buff 直接當治療來源。目前只在已確認的週期治療 status 中找來源；單一來源直接歸屬，多來源依 tooltip potency 權重拆分，無候選時保留在「無法歸屬的持續治療」，不硬塞給玩家也不丟失總量。目前已收錄陽星合相、命運之輪、天星衝日、仙光的低語、極光、持續擺脫、活性紋、討罪、泰然自若、通天眼與河流神之瓶。

目前陽星合相 HoT 使用官方 175 potency、河流神之瓶使用官方 200 potency；先前把河流神之瓶誤寫成 100，會在兩者重疊時把同一個合併 tick 過少分給河流神之瓶。potency 權重只能守恆拆分封包總量， 仍無法還原兩個 HoT 各自獨立的隨機浮動值。

NetworkDoT 行中的 current HP 是 tick 結算後快照，不能當作治療前 HP；技能 HoT 的有效量使用該目標前一筆 HP cache，再由同一 healing frame 依序扣除已歸因量。

同一行的 source HP 也是週期效果攜帶的舊快照，不保證是事件當下的即時 HP，因此不能用它回寫 source 的 HP cache。XDt7a138MhLqNbkx / fight=last 中，占星已被 Lady of Crowns 的 line 37 補滿至 154,399，45ms 後的他人 HoT line 24 仍攜帶舊值 129,080；若回寫，下一筆 line 39 會憑空產生 1,543 自然回血。

合併 HoT 的封包 amount 不包含自然生命再生。生命再生來自 NetworkUpdateHP（39）行，不可依賴 effectId=0：沒有任何技能 HoT 時，39 行仍會單獨出現。實際使用量為：

text
生命再生 = min(floor(目標最大 HP × 1%),
                max(0, 39 行 current HP - 前一筆 HP cache current HP))

生命再生只記實際增加的 HP，沒有 overheal，且不能從合併 HoT amount 中扣除。此公式在 XDt7a138MhLqNbkx / fight=last 的逐事件對帳中，黑魔為 48 次、71,689，占星為 42 次、64,806， 兩者都與 FFLogs 完全一致。

有效護盾(估) 不是護盾產生量，也尚未等同 FFLogs 平台 absorbs，而是敵方 action 傷害或 DoT tick 打到玩家時，以前後 HP 差推估實際被 shield 吃掉的傷害。已知容量的有限次護盾若在自然期限前移除，會以容量補足同 frame HP 快照未顯示的已耗部分；自然到期不計。殘暴彈會被連段頻繁重上，提前移除仍須同時有 1 秒內的受傷證據，避免把覆蓋誤當消耗。

擺脫的基本護盾容量是 floor(目標施放當下最大 HP × 15%)；不能因技能最多可強化到 21%，就一律套 21% 上限。每層以獨立狀態實例追蹤已消耗量；傷害差額或 30 秒自然期限前的狀態移除可證明已耗盡，自然到期則不計。不同盾重疊、無法判定吸收順序時仍保守不歸因。

戰士的原初的血氣會同時套用多個狀態；其中 4 秒的 A77 原初的血潮 是減傷，20 秒的 A78 原初的血煙 才是 Stem the Tide 護盾。護盾狀態必須收錄 A78，不能把 A77 減傷誤算成吸收，也不能只把 A76 原初的血氣 的自療算進治療。

已確認的治療量轉盾容量依技能規則計算並對結果向下取整：陽星合相的護盾（server-side status F36） 為 floor(該次回復量 × 125%)、天星交錯為 floor(× 200%)、鼓舞為 floor(× 180%)；鼓舞暴擊時的 77E 激勵 是另一層獨立 floor(× 180%) 護盾，不能與鼓舞合併或漏算。

中間學派 (781) vs 陽星合相護盾 (F36)：ACT network log 中 781（中間學派）是 AST 職業姿態標記， 不是護盾；陽星合相的護盾 status 在 server-side 記錄為 F36（15 秒），FFLogs 以 client-side ID 0x781 稱呼。 兩者不可混用——F36 才應收錄為護盾狀態，781 不應計入吸收。

展開戰術 E01 不會替擴散目標再送一筆 healing effect；它只送技能事件與後續 129 鼓舞 狀態。擴散盾容量必須複製施放當下同來源仍有效的原始鼓舞容量，再各自追蹤實際消耗；不能把 7 個 目標當成沒有容量的普通狀態，也不能重算 7 次治療。

建築神之塔（F34）是 400 potency AoE barrier-only 技能。ACT 每次施放只記錄 1 筆 type 26 status apply （對應 action line target），其餘 7 名隊友的套用事件被略過；Parser 在 type 22 action 行偵測到 90A1 時， 會主動為 pull.players 中所有已知玩家預先注冊 F34（duration 30s），確保後續傷害可完整歸因。F34 沒有直接 heal amount 可換算容量時，第一次有受傷證據且提前耗盡的實例以 HP 差額學得保守基準，後續同來源實例用 該基準補足同 frame 缺口。PullDetector 會把開戰前 60 秒內的 26/30 帶入 pull；這些事件只建立狀態， 不改變 pull 起點。若 F34 與 F36 同時存在，依 FFLogs 逐事件確認的順序先分配 F34、再分配 F36；兩者容量 耗盡後不把殘留的 server-frame 假差額繼續灌給其他盾。未重建出完整 400 potency 公式前，不用 10% 最大 HP 或報告專用常數代替。

限制：

  • 戰鬥初期 HP cache 未建立時，fallback 把原始治療全算有效 → 短 pull 的有效治療可能略偏高。
  • 有效護盾(估) 仍未等同 FFLogs 平台 absorbs；不同來源玩家的多盾同時存在、HP 快照缺漏或無法歸因時不硬算。
  • 致死傷害若包含 overkill，或單筆 raw damage 已超過目標最大 HP，raw damage - HP loss 無法證明差額是護盾吸收，因此不計有效盾；避免團滅技的數百萬溢出傷害被誤算成有效治療。
  • Horoscope 762 / 763 目前作為多盾衝突 blocker，不直接把 HP loss 歸給它們；避免在證據不足時高估 AST absorbs。
  • 強化擺脫額外的每層 2% 必須由施放時實際消耗的防禦效果判定；目前未辨識到該證據時採基本 15%，不以 21% 上限代替。
  • 陽星合相 F36 type 26 status apply 比 type 22 heal 晚約 1 秒送達；這 1 秒內的傷害吸收可能無法歸因到 F36。
  • F34 保守基準仍受限於 HP snapshot 缺漏；若後續取得完整 potency 公式，可用精確容量替換 learned 機制。

實作：report/accumulator.ts 的 estimateEffectiveHealing / estimateEffectiveShielding、report/rhps.ts、pullSummary.ts 與 PlayerHealingTable.vue。

技能施放 ​

Casts / CPM ​

Casts = 玩家 action 次數（含純 buff、utility、落空的施放）
CPM = Casts / (戰鬥秒數 / 60)

排除：自動攻擊、DoT/HoT tick 本身。 AOE 多目標用 timestamp + player + ability 去重成一次施放。

實作：report/accumulator.ts 的 addPlayerCastEvent。

GCD 使用率 ​

每次已知 GCD 技能施放 → 視為一段 [施放時間, 施放時間 + recast] 的鎖定區間
GCD uptime% = 合併重疊區間後的總長度 / 戰鬥秒數

只有 ability metadata 收錄的 GCD 技能會納入（recast 預設 2.5s，部分技能有特別值），未知技能不硬算。

實作：pullSummary.ts 的 getGcdMetrics。

威力估算 ​

威力（potency）來源 ​

  1. 優先用 XIVAPI action metadata 的 potency（含 description 解析）。
  2. 缺 metadata 的傷害事件，用同場次已知事件的比例推估：
damagePerPotency = 已知事件總傷害 / 已知事件總威力
推估威力 = 該事件傷害 / damagePerPotency

UI 進度條：深綠 = 直接 metadata、淺綠 = 傷害比例推估。

限制：buff 期間傷害偏高會讓推估威力略偏高；傷害為 0 的事件無法推估。

實作：analysis/rotationAnalyzer.ts 的 analyzePotency。

Buff 期間威力 / 覆蓋率 ​

Buff 期間威力 = 落在任一已收錄 buff 視窗內的事件威力總和
Buff 覆蓋率 = Buff 期間威力 / 總威力

buff 視窗只計已收錄的 raid buff / personal buff（3–45 秒的短效增益），排除坦姿、食物等長效狀態。

Pull 切分與階段 ​

Pull 切分 ​

三層 inactivity 門檻（預設 inactivityGapSeconds = 45 秒，可用 PULL_GAP_SECONDS 環境變數調整）：

滅團中（多數玩家死亡且未復活行動）→ min(inactivityGapSeconds, 20) 秒安靜就切
戰鬥中（主目標存活、未滅團）      → inactivityGapSeconds × 2（預設 90 秒，容許過場動畫）
其他                              → inactivityGapSeconds（預設 45 秒）

輔助規則：

  • 滅團偵測：玩家死亡（line 25，含環境殺 E0000000）加入死亡名單；之後施放技能（21/22）視為已復活移除。死亡中人數 ≥ max(4, 玩家數 × 0.75) 判定滅團。
  • 起點：非玩家來源對玩家的純治療（例如開戰前仙女的 仙光的擁抱）不會自行開啟 pull；pull 已開始時仍會進入治療統計。
  • 終點：主目標的 action HP snapshot 或 37 / 38 / 39 actor state 顯示 HP 歸零時立即結束；line 25 death 仍是備援。王死亡後的殘留 HoT、寵物治療不延長分母。
  • target swap 關閉：只有主目標「已死亡」後出現新的大血量目標才切新 pull；主目標活著時的新大目標視為同場戰鬥的階段角色或 add。
  • 主目標升級：血量 ≥ 現任主目標 1.2 倍的新形態會接手主目標身分（例如究極武器最終階段），pull 名稱才會對到玩家認知的 boss。

實作：pull/rules.ts、detectPulls.ts。

階段切分 ​

每個大型目標（boss 級 HP）「首次被玩家攻擊」記為一個階段起點
階段結束 = 下一個階段的開始（最後一段到 pull 結束）

只認玩家主動攻擊（21/22）——大血量 add 攻擊玩家不算接戰，避免妙翅、爆破岩石這類 add 被誤標成階段。同名目標重複出現（如亂流階段）不會切出新階段。

每個階段產生完整報表（phaseReports[]）：所有表格從逐筆事件重算，與整場用同一套公式（DPS、rDPS*、Crit、治療、承傷、死亡、Casts、GCD uptime）。

限制：階段時間窗以「下一個 boss 首次被攻擊」為界，過場與中間 add 潮（亂流）會算在前一階段內。

實作：detectPulls.ts 的 trackPhaseMarker、pullSummary.ts 的 toPhaseReport。

Kill / Wipe 判定 ​

kill：勝利系統訊息（寶箱出現）或 primary target 死亡
wipe：死亡玩家名數 ≥ max(4, 玩家數 × 0.75)
其餘：unknown

階段報表只有最後一個階段繼承整場結果（boss 在該階段倒下）。

實作：pullSummary.ts 的 inferResult。

做不到 / 不做的 ​

指標原因
Parse percentile（色字）需要 FFLogs 全站同職業/同副本分布資料庫
