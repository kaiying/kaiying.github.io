計算公式說明 ​

這份文件整理本專案所有指標的計算公式、資料來源與已知限制。 想知道「某個數字怎麼算出來的」，先查這裡。

實作位置以 src/parser/ 為準；FFLogs 對照請見 fflogs-metrics-reference.md 與 recommend.md。

傷害公式 ​

DPS ​

DPS = 有效傷害 / 戰鬥秒數
戰鬥秒數 = pull end - pull start

實作：report/metrics.ts 的 toActorMetrics。

有效傷害（overkill 排除） ​

對齊 FFLogs 的 effective damage 口徑：

有效傷害 = min(原始傷害, 目標當下剩餘 HP)

超過目標剩餘血量的部分（overkill，殺敵瞬間的溢出傷害）不計入。 目標 HP 來自 log line 的 HP 快照（action line 為 fields[24]/[25]、DoT tick 為 fields[7]/[8]，即被 tick 實體的 HP），缺漏時 fallback 到 HP cache。

限制：同一 server frame 的多筆命中共用同一 HP 快照，overkill 是估算而非精確值；快照缺漏或為 0 時不裁切，避免誤刪整筆傷害。

實作：report/accumulator.ts 的 toEffectiveDamage。

rDPS* ​

與 FFLogs 的 rDPS 概念相同、精度不同，所以標了 *：

rDPS* = (個人有效傷害 - 吃到的外部 raid buff 收益 + 自己提供給隊友的 raid buff 收益) / 戰鬥秒數

buff 收益估算：

基準傷害 = 實際傷害 / 所有生效 buff 的總倍率
額外傷害 = 實際傷害 - 基準傷害
多 buff 疊加時，額外傷害依各 buff 的增傷權重 (倍率-1) 拆分給提供者

與 FFLogs 的差距：只收錄已驗證的 raid buff metadata；Crit/DH 類 buff（連環計、戰鬥連禱）用保守期望值常數（每 1% crit rate ≈ 0.5% 增傷、每 1% DH rate ≈ 0.25% 增傷），不是依玩家副屬性精算。

實作：report/rdps.ts 的 estimateRaidBuffContributions。

DoT 的 buff 歸因（snapshot） ​

DoT tick 的 buff 歸因用狀態施加當下（snapshot），不是 tick 發生時間——符合 FFXIV 的 DoT snapshot 機制：

DoT tick 的歸因時間 = 該 DoT 狀態最後一次施加的時間（snapshotOffsetSeconds）
直接傷害的歸因時間 = 事件發生時間

所以在 raid buff 視窗內上的 DoT，buff 結束後的 tick 仍算進 buff 貢獻。

限制：合併 tick（effectId 0）用「同來源、同目標」的作用中狀態回推，可能配到同來源的非 DoT debuff（如牽制），owner 正確但 snapshot 時間可能取到鄰近狀態。

實作：report/accumulator.ts（addTickReportEvent）＋ report/rdps.ts。

Boss / add 傷害分類 ​

沒有 encounter 資料庫，用 HP heuristic：

boss 候選 = 目標最大 HP ≥ 玩家最大 HP × 8

再依 primary target、BNpc 資訊細分 boss / add / object / pet。分類結果影響 bossDamage / addDamage 等統計，不影響總傷害。

實作：targetClassification.ts、pull/rules.ts 的 isPrimaryTargetCandidate。

Crit / Direct Hit ​

Crit / DH / CDH ​

Crit% = crit hits / hits
DH%   = direct hits / hits
CDH%  = 同時爆擊且直擊的 hits / hits

crit/DH 從 action effect flags 讀取（bit 0x2000 = crit、0x4000 = direct hit）。

限制：DoT tick（line 24）沒有 flags，計入分母但一律視為非爆擊，所以 DoT 重職業的顯示值會比實際爆擊率低。

實作：actionEffect.ts（flags 解析）、report/metrics.ts（比率計算）。

治療公式 ​

HPS（有效治療） ​

表上的 HPS 就是 effective HPS（eHPS），已排除過量治療，與 FFLogs 的「HPS」同口徑：

HPS = 有效治療 / 戰鬥秒數
有效治療 = min(原始治療量, 目標最大 HP - 目標當前 HP)

包含 overheal 的版本叫 raw HPS（表上的「原始治療」欄位除以時間）。

限制：

  • 戰鬥初期 HP cache 未建立時，fallback 把原始治療全算有效 → 短 pull 的 HPS 略偏高。
  • 護盾（shield/absorb）尚未解析，賢者/學者的盾量不計入有效治療。

實作：report/accumulator.ts 的 estimateEffectiveHealing。

過量治療（Overheal） ​

過度治療 = 原始治療 - 有效治療
過治% = 過度治療 / 原始治療

技能施放 ​

Casts / CPM ​

Casts = 玩家 action 次數（含純 buff、utility、落空的施放）
CPM = Casts / (戰鬥秒數 / 60)

排除：自動攻擊、DoT/HoT tick 本身。 AOE 多目標用 timestamp + player + ability 去重成一次施放。

實作：report/accumulator.ts 的 addPlayerCastEvent。

GCD 使用率 ​

每次已知 GCD 技能施放 → 視為一段 [施放時間, 施放時間 + recast] 的鎖定區間
GCD uptime% = 合併重疊區間後的總長度 / 戰鬥秒數

只有 ability metadata 收錄的 GCD 技能會納入（recast 預設 2.5s，部分技能有特別值），未知技能不硬算。

實作：pullSummary.ts 的 getGcdMetrics。

威力估算 ​

威力（potency）來源 ​

  1. 優先用 XIVAPI action metadata 的 potency（含 description 解析）。
  2. 缺 metadata 的傷害事件，用同場次已知事件的比例推估：
damagePerPotency = 已知事件總傷害 / 已知事件總威力
推估威力 = 該事件傷害 / damagePerPotency

UI 進度條：深綠 = 直接 metadata、淺綠 = 傷害比例推估。

限制：buff 期間傷害偏高會讓推估威力略偏高；傷害為 0 的事件無法推估。

實作：analysis/rotationAnalyzer.ts 的 analyzePotency。

Buff 期間威力 / 覆蓋率 ​

Buff 期間威力 = 落在任一已收錄 buff 視窗內的事件威力總和
Buff 覆蓋率 = Buff 期間威力 / 總威力

buff 視窗只計已收錄的 raid buff / personal buff（3–45 秒的短效增益），排除坦姿、食物等長效狀態。

Pull 切分與階段 ​

Pull 切分 ​

三層 inactivity 門檻（預設 gap 45 秒）：

滅團中（多數玩家死亡且未復活行動）→ 20 秒安靜就切
戰鬥中（主目標存活、未滅團）      → 90 秒（容許過場動畫）
其他                              → 45 秒

輔助規則：

  • 滅團偵測：玩家死亡（line 25，含環境殺 E0000000）加入死亡名單；之後施放技能（21/22）視為已復活移除。死亡中人數 ≥ max(4, 玩家數 × 0.75) 判定滅團。
  • target swap 關閉：只有主目標「已死亡」後出現新的大血量目標才切新 pull；主目標活著時的新大目標視為同場戰鬥的階段角色或 add。
  • 主目標升級：血量 ≥ 現任主目標 1.2 倍的新形態會接手主目標身分（例如究極武器最終階段），pull 名稱才會對到玩家認知的 boss。

實作：pull/rules.ts、detectPulls.ts。

階段切分 ​

每個大型目標（boss 級 HP）「首次被玩家攻擊」記為一個階段起點
階段結束 = 下一個階段的開始（最後一段到 pull 結束）

只認玩家主動攻擊（21/22）——大血量 add 攻擊玩家不算接戰，避免妙翅、爆破岩石這類 add 被誤標成階段。同名目標重複出現（如亂流階段）不會切出新階段。

每個階段產生完整報表（phaseReports[]）：所有表格從逐筆事件重算，與整場用同一套公式（DPS、rDPS*、Crit、治療、承傷、死亡、Casts、GCD uptime）。

限制：階段時間窗以「下一個 boss 首次被攻擊」為界，過場與中間 add 潮（亂流）會算在前一階段內。

實作：detectPulls.ts 的 trackPhaseMarker、pullSummary.ts 的 toPhaseReport。

Kill / Wipe 判定 ​

kill：勝利系統訊息（寶箱出現）或 primary target 死亡
wipe：死亡玩家名數 ≥ max(4, 玩家數 × 0.75)
其餘：unknown

階段報表只有最後一個階段繼承整場結果（boss 在該階段倒下）。

實作：pullSummary.ts 的 inferResult。

做不到 / 不做的 ​

指標原因
Parse percentile（色字）需要 FFLogs 全站同職業/同副本分布資料庫
aDPS需要 FFLogs 官方的 per-job padding buff 規則
精確 mitigation（減傷量）需要技能原始威力或未減傷樣本
護盾量（absorb）shield effect 尚未解析（排在 P4）
機制分析需要 encounter metadata（已移除骨架，見 git 歷史）

更新原則 ​

改了任何公式：

  1. 對應更新這份文件。
  2. bump parserVersion（src/web/storage/logStore.ts），讓 IndexedDB 自動 reparse。
  3. npm run parse 重新產生 public data。
  4. 版本歷史記在 local-parser-notes.md。
