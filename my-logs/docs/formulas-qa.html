計算公式說明 ​

這份文件整理本專案所有指標的計算公式、資料來源與已知限制。 想知道「某個數字怎麼算出來的」，先查這裡。

實作位置以 src/parser/ 為準。

例外：減傷歸因規格 是 2026-09-10 工作包 C 的待實作／待驗證設計， 不是現行報表公式；其數學驗收不代表已對齊 FFLogs。

傷害公式 ​

DPS ​

DPS = 有效傷害 / 戰鬥秒數
戰鬥秒數 = pull end - pull start

Limit Break 若技能名稱或 ability ID 在 limitBreak.ts 的辨識清單內，會獨立成 Limit Break 傷害列，不掛在施放玩家身上；總傷害仍包含 Limit Break。目前已驗證清單包含 C5、C8、C9、CA、1EB5、1EB6；未收錄的職業 LB3 仍會被歸到施放玩家的 DPS。

實作：report/metrics.ts 的 toActorMetrics。

有效傷害（overkill 排除） ​

對齊 FFLogs 的 effective damage 口徑：

有效傷害 = min(原始傷害, 目標當下剩餘 HP)

超過目標剩餘血量的部分（overkill，殺敵瞬間的溢出傷害）不計入。 目標 HP 來自 log line 的 HP 快照（action line 為 fields[24]/[25]、DoT tick 為 fields[7]/[8]，即被 tick 實體的 HP），缺漏時 fallback 到 HP cache。

限制：同一 server frame 的多筆命中共用同一 HP 快照，overkill 是估算而非精確值；快照缺漏或為 0 時不裁切，避免誤刪整筆傷害。

實作：report/effectCalc.ts 的 toEffectiveDamage。

rDPS* ​

與 FFLogs 的 rDPS 概念相同、精度不同，所以標了 *：

rDPS* = (個人有效傷害 - 吃到的外部 raid buff 收益 + 自己提供給隊友的 raid buff 收益) / 戰鬥秒數

buff 收益估算：

基準傷害 = 實際傷害 / 所有生效 buff 的總倍率
額外傷害 = 實際傷害 - 基準傷害
多 buff 疊加時，額外傷害依各 buff 的增傷權重 (倍率-1) 拆分給提供者

與 FFLogs 的差距：只收錄已驗證的 raid buff metadata；Crit/DH 類 buff（連環計、戰鬥連禱）用保守期望值常數（每 1% crit rate ≈ 0.5% 增傷、每 1% DH rate ≈ 0.25% 增傷），不是依玩家副屬性與事件 crit/DH portion 精算。連環計 metadata 已收錄，但它是套在敵人身上的 target debuff，目前 target-debuff 型 attribution 仍在 doc/fflogs-rdps-validation-plan.md 的 M3 跟進。

實作：report/rdps.ts 的 estimateRaidBuffContributions。

DoT 的 buff 歸因（snapshot） ​

DoT tick 的 buff 歸因用狀態施加當下（snapshot），不是 tick 發生時間——符合 FFXIV 的 DoT snapshot 機制：

DoT tick 的歸因時間 = 該 DoT 狀態最後一次施加的時間（snapshotOffsetSeconds）
直接傷害的歸因時間 = 事件發生時間

所以在 raid buff 視窗內上的 DoT，buff 結束後的 tick 仍算進 buff 貢獻。

限制：合併 tick（effectId 0）用「同來源、同目標」的作用中狀態回推，可能配到同來源的非 DoT debuff（如牽制），owner 正確但 snapshot 時間可能取到鄰近狀態。

實作：report/tickProcessor.ts 的 addTickReportEvent ＋ report/rdps.ts。

Boss / add 傷害分類 ​

沒有 encounter 資料庫，用 HP heuristic：

boss 候選 = 目標最大 HP ≥ max(100,000, 玩家最大 HP × 8)

再依 primary target、BNpc 資訊細分 boss / add / object / pet。分類結果影響 bossDamage / addDamage 等統計，不影響總傷害。

實作：targetClassification.ts、pull/rules.ts 的 isPrimaryTargetCandidate。

Crit / Direct Hit ​

Crit / DH / CDH ​

Crit% = crit hits / hits
DH%   = direct hits / hits
CDH%  = 同時爆擊且直擊的 hits / hits

crit/DH 從 action effect flags 讀取（bit 0x2000 = crit、0x4000 = direct hit）。

限制：DoT tick（line 24）沒有 flags，計入分母但一律視為非爆擊，所以 DoT 重職業的顯示值會比實際爆擊率低。

ACT overlay 對帳工具另採「只有帶 action flags 的事件才進 Crit／DH／CDH 分母」的相容口徑，並仍以全部 正傷害事件計算 Swing。這只用於 overlay validation，不改變網站主表公式；Swing 是否包含 miss、zero damage 與其他 ACT swing type 尚未完全確認。

實作：actionEffect.ts（flags 解析）、report/metrics.ts（比率計算）。

治療公式 ​

網站主治療指標優先採 FFLogs healing category 概念：有效 direct heal 與實際 absorb 都算 healing，overheal 不算 HPS。ACT overlay 的 raw Healed 口徑只保留在對帳工具。

Action packet 的直接治療只計 effect type 04；critical heal 仍是 04，差異寫在 severity flags。 1B（combo/action marker）、0E / 0F（狀態套用）與 0B（MP 回復）的 payload 不是 HP 回復量，不能併入 raw healing。NetworkDoT（24）的 HoT 則走下述獨立 tick 規則。

戰鬥摘要 ​

摘要卡片的治療數字來自整場 pull 彙總：

有效治療 = sum(玩家有效治療)
原始治療 = sum(玩家原始治療)
過度治療 = 原始治療 - 有效治療
戰鬥摘要過治% = 過度治療 / 原始治療

實作：pullSummary.ts 的 overhealPercent。

治療表 HPS（目前網站口徑） ​

網站主表的 HPS 欄：

HPS = (有效治療 + 有效護盾(估)) / pull duration seconds

護盾只有在被傷害實際吸收後才算有效；施放後仍剩餘、未被打掉的盾不進 HPS。即 有效治療 欄位的「直接治療 + 已耗盾」除以戰鬥秒數。

網站另顯示 FFLogs 概念的本地估算 rHPS*：

受治療增益額外量 = effective heal - effective heal / 所有外部受治療倍率乘積
rHPS* = (有效治療 + 已耗盾 + 增益提供量 - 外部增益接受量) / pull duration seconds

目前已驗證並納入：鐵壁（15%）、戰慄（20%）、生命回生法（10%）。只重新歸因已發生的有效治療，不把 overheal、未消耗護盾或無法歸屬的 HoT 搬移。全隊增益提供量與接受量守恆，因此團隊 HPS 與團隊 rHPS* 總和相同。星號表示 healing buff metadata 尚未完整，不能宣稱等同 FFLogs rHPS。

目前本地可直接對帳的子口徑是 FFLogs healing 的「effective healing + absorbs、mitigation 關閉」： 包含有效治療與實際吸收，但不含 mitigation。它不是使用者開啟報告 URL 時看到的 FFLogs 預設 Healing 主表；兩者不得共用同一個 Amount / HPS 基準。FFLogs 預設表的 mitigation 必須由逐筆 calculateddamage 事件中的 mitigated、unmitigatedAmount 與 packetId 驗證後再實作，不能用兩張 總表的差額回填。

ACT overlay 對帳工具仍按截圖欄位計算：

Overlay Healed = Eff.Heal + OverHeal + D.Shield
               = 原始治療 + D.Shield

pull duration seconds 是本地偵測的戰鬥秒數，也就是 pull end - pull start。FFLogs 的精確分母應取 該 fight 的 endTime - startTime；目前兩者仍有邊界差異。overlay 對帳工具為了比對截圖，會另外 使用 active damage duration；那又是另一個口徑。

治療表欄位 ​

有效直接治療 = min(原始治療量,
                    同 packet id 的 NetworkActionSync(37) current HP - 結算前 HP cache current HP)
有效治療（主表） = 有效直接治療 + 已被傷害消耗的有效護盾(估)
原始治療 = heal / HoT effect 的 raw amount
過度治療 = 原始治療 - 有效治療
治療表過治% = 過度治療 / (原始治療 + 已耗盾)

NetworkAbility / NetworkAOEAbility（21/22）是 calculation/preparation，不是治療已實際生效的時間點。 直接治療先依 action packet sequence 與目標暫存 raw amount；收到相同 packet id 的 NetworkActionSync（37）後，才以前後 HP 實際增量依原事件順序分配 effective，剩餘為 overheal。 無 packet id 的舊格式才退回 HP snapshot healing frame 估算。

v58 的 HP cache 防止已確認的舊 action 快照重播：37 改變某 actor 的 current HP 時，暫存被取代的 current／max。後到的 21／22 若與該 37 同毫秒、且兩個 HP 欄位完整等於被取代的快照，就不回寫 cache；target 24／25 與 source 34／35 都適用。原始 action 快照仍保留於診斷，不替換 packet 值，也不補 pending effective。若 action 對該目標帶正傷害，先清除這份重播證據；不同 HP／max HP、較晚 timestamp 或中間已接受的不同 HP 狀態照常更新。這是同毫秒且精確重播的有限保護，不是 HP 只增不減，也不代表任意 37／38／39 永遠優先於 action。

NetworkDoT 的 HoT effectId=0 是技能 HoT 的合併 tick，不可把封包 source 或任意 active buff 直接當治療來源。目前只在已確認的週期治療 status 中找來源；單一來源直接歸屬，多來源依 tooltip potency 權重拆分，無候選時保留在「無法歸屬的持續治療」，不硬塞給玩家也不丟失總量。目前已收錄陽星合相、命運之輪、天星衝日、仙光的低語、極光、持續擺脫、活性紋、討罪、泰然自若、通天眼與河流神之瓶。

目前陽星合相 HoT 使用官方 175 potency、河流神之瓶使用官方 200 potency；先前把河流神之瓶誤寫成 100，會在兩者重疊時把同一個合併 tick 過少分給河流神之瓶。potency 權重只能守恆拆分封包總量， 仍無法還原兩個 HoT 各自獨立的隨機浮動值。

NetworkDoT 行中的 current HP 是 tick 結算後快照，不能當作治療前 HP；技能 HoT 的有效量使用該目標前一筆 HP cache，再由同一 healing frame 依序扣除已歸因量。

同一行的 source HP 也是週期效果攜帶的舊快照，不保證是事件當下的即時 HP，因此不能用它回寫 source 的 HP cache。XDt7a138MhLqNbkx / fight=last 中，占星已被 Lady of Crowns 的 line 37 補滿至 154,399，45ms 後的他人 HoT line 24 仍攜帶舊值 129,080；若回寫，下一筆 line 39 會憑空產生 1,543 自然回血。

合併 HoT 的封包 amount 不包含自然生命再生。生命再生來自 NetworkUpdateHP（39）行，不可依賴 effectId=0：沒有任何技能 HoT 時，39 行仍會單獨出現。實際使用量為：

text
生命再生 = min(floor(目標最大 HP × 1%),
                max(0, 39 行 current HP - 前一筆 HP cache current HP))

生命再生只記實際增加的 HP，沒有 overheal，且不能從合併 HoT amount 中扣除。此公式在 XDt7a138MhLqNbkx / fight=last 的逐事件對帳中，黑魔為 48 次、71,689，占星為 42 次、64,806， 兩者都與 FFLogs 完全一致。

有效護盾(估) 不是護盾產生量，也尚未等同 FFLogs 平台 absorbs，而是敵方 action 傷害或 DoT tick 打到玩家時，以前後 HP 差推估實際被 shield 吃掉的傷害。已知容量的有限次護盾若在自然期限前移除，會以容量補足同 frame HP 快照未顯示的已耗部分；自然到期不計。殘暴彈會被連段頻繁重上，提前移除仍須同時有 1 秒內的受傷證據，避免把覆蓋誤當消耗。

擺脫的基本護盾容量是 floor(目標施放當下最大 HP × 15%)；不能因技能最多可強化到 21%，就一律套 21% 上限。每層以獨立狀態實例追蹤已消耗量；傷害差額或 30 秒自然期限前的狀態移除可證明已耗盡，自然到期則不計。不同盾重疊、無法判定吸收順序時仍保守不歸因。

戰士的原初的血氣會同時套用多個狀態；其中 4 秒的 A77 原初的血潮 是減傷，20 秒的 A78 原初的血煙 才是 Stem the Tide 護盾。護盾狀態必須收錄 A78，不能把 A77 減傷誤算成吸收，也不能只把 A76 原初的血氣 的自療算進治療。

已確認的治療量轉盾容量依技能規則計算並對結果向下取整：中間學派期間的陽星合相護盾為 floor(該次回復量 × 125%)、天星交錯為 floor(× 200%)、鼓舞為 floor(× 180%)；鼓舞暴擊時的 77E 激勵 是另一層獨立 floor(× 180%) 護盾，不能與鼓舞合併或漏算。

中間學派護盾 (781) vs 陽星合相 HoT (F36)：ACT network log 中，中間學派期間的 陽星合相 action 會在同一 server frame 對每個目標套用 30 秒 781，這才是 floor(該次回復量 × 125%) 的 barrier 狀態。781 若在 30 秒前移除，可作為護盾已耗盡的 逐目標證據；自然到期不補計未消耗餘額。F36 是陽星合相的 15 秒 HoT 狀態，不是 barrier，不能因為與 781 同時存在就把 F36 當成護盾。

展開戰術 E01 不會替擴散目標再送一筆 healing effect；它只送技能事件與後續 129 鼓舞 狀態。擴散盾容量必須複製施放當下同來源仍有效的原始鼓舞容量，再各自追蹤實際消耗；不能把 7 個 目標當成沒有容量的普通狀態，也不能重算 7 次治療。

建築神之塔（F34）是 400 potency AoE barrier-only 技能。ACT 每次施放只記錄 1 筆 type 26 status apply， 其餘隊友的套用事件缺失；Parser 只追蹤封包實際提供的目標，不再從 type 22 合成全隊 F34，避免把缺 HP snapshot 的 server-frame 差額灌進無直接證據的隊員。F34 沒有直接 heal amount 可換算容量時，第一次有受傷 證據且提前耗盡的實例以 HP 差額學得保守基準，後續同來源實例可用該基準補足同 frame 缺口。PullDetector 會把開戰前 60 秒內的 26/30 帶入 pull；這些事件只建立狀態，不改變 pull 起點。若 F34 與可確認的 781 護盾同時存在，先分配 F34、再分配 781。未重建出完整 400 potency 公式前，不用報告專用常數補差額。

限制：

  • 戰鬥初期 HP cache 未建立時，fallback 把原始治療全算有效 → 短 pull 的有效治療可能略偏高。
  • 有效護盾(估) 仍未等同 FFLogs 平台 absorbs；不同來源玩家的多盾同時存在、HP 快照缺漏或無法歸因時不硬算。
  • 完全被護盾吃掉的 type 22 action 可能同時回報 damage amount 0 與不變的 HP snapshot；此時封包只證明 active shield 候選存在，沒有可計算的吸收量。XDt7a138MhLqNbkx / fight=last 的三筆鼓舞事件因此少計 82,390，debug trace 會標成 no-estimated-absorb，正式報表不以 FFLogs 差額回填。
  • 致死傷害若包含 overkill，或單筆 raw damage 已超過目標最大 HP，raw damage - HP loss 無法證明差額是護盾吸收，因此不計有效盾；避免團滅技的數百萬溢出傷害被誤算成有效治療。
  • Horoscope 762 / 763 目前作為多盾衝突 blocker，不直接把 HP loss 歸給它們；避免在證據不足時高估 AST absorbs。
  • 強化擺脫額外的每層 2% 必須由施放時實際消耗的防禦效果判定；目前未辨識到該證據時採基本 15%，不以 21% 上限代替。
  • 中間學派護盾 781 與 type 22 heal 同 frame 送達；同 frame 多筆傷害仍受 HP snapshot 粒度限制。
  • F34 只追蹤封包可見目標，因此必然低估未送出 type 26 的隊員；這比合成全隊狀態造成假吸收保守。

實作：report/effectCalc.ts 的 estimateEffectiveHealing / estimateEffectiveShielding、report/rhps.ts、pullSummary.ts 與 PlayerHealingTable.vue。

直接治療配對診斷（不改公式） ​

debug:healing -- <log> <pull> pairs [ability|*] [target|*] [start] [end] 保存 preparation／resolve、sequence、結算前 HP 來源行號及 pending／resolved／missing-hp。Preparation 當下另保存兩組互不替代的 HP／maxHP 證據：

  • preparation.packetHp：使用 action processor 已解析的 healingTargetHp，一般治療（含以自己為 target 的治療）取 target 欄位 24／25；攻擊附帶的 secondary self-heal 取 self 欄位 34／35。slot 明示來源，每個值保存 raw 欄位、type、timestamp、原始檔 lineNumber 與從 0 起算的 fieldIndex。
  • preparation.cachedHp：保存處理該 action 前既有的 HP cache 與各值來源；不以當次 packet 覆蓋這份證據。Type 37 僅更新 current HP，因此 maxHP 的來源仍是先前提供 maxHP 的封包。沒有來源行號時省略，不杜撰；只有 cache 數值時也不宣稱已知來源。

preparation.snapshotState 只表示 preparation snapshot full／injured／unknown：packet 的有效 HP 等於 maxHP 為 full，0 ≤ HP < maxHP 為 injured；缺值、空白、非有限數、負 HP、非正 maxHP 或 HP 超過 maxHP 為 unknown。每個欄位另記 valid／missing／invalid，缺值不轉成 0 或滿血；無效值保留 raw 供追查。Packet 缺失或無效時不以 cache 冒充當次快照；兩者不一致時均保留。CLI 同時列出選取事件與其中 pending 的三類計數，因此不必等待 resolve 才能檢查 preparation 證據。封包快照不保證是事件當下的即時 HP，這些分類不能宣稱有效治療或可用治療容量。

這是 debug draft 的旁路紀錄，不加入正式 report／IndexedDB；診斷關閉時不收集，也不參與治療計算。陽星＋自然回血 fixture 固定有效治療 13,039／7,903，詳見 治療稽查。pending 只表示尚未配對，不能推成全部 raw healing 有效。純診斷更動不影響公式、儲存 schema 或 parserVersion。

減傷歸因規格（待實作／待驗證） ​

本節只定義候選模型、證據需求與驗收，不改上述 HPS／rHPS*／有效盾公式，不新增 runtime、 shared types 或 HPS 切換；本規格未獨立更動 parserVersion。Healing 主線及逐事件資料前提滿足後才可接續實作， rDPS 改造不在此工作包。以下「必須」是未來實作的驗收條件。

總量模型與量綱 ​

以下是條件式數學模型，不是已核實的全遊戲傷害管線。限同一事件的已知、可疊加百分比減傷， 每項 0 <= r_i < 1；互斥、覆蓋、強化版本先依 metadata 解決，不把相同狀態的重複記錄當成多層。

text
D0 = 移除本次歸因集合中的百分比減傷、保留其餘條件時的反事實傷害
q  = product(1 - r_i)
D  = D0 × q                  # 百分比減傷後、扣盾前，未裁切 overkill
M  = D0 - D = D × (1/q - 1)  # 僅本次集合的減傷總量；q > 0

D0 不是技能 potency，也不一定是 FFLogs unmitigatedAmount：本模型將護甲、被動特性、 格擋／招架及易傷等未納入分攤的條件固定在基準中。若它們不能分離、會與所選減傷交互作用， 或該攻擊不遵循乘法模型，總量降級未知。不能拿包含護甲的 API mitigated 全數分給玩家。 只要 D 與完整 q 可確認，就不必另找未減傷樣本；但整數取整會使反推值成為估算。 只有原始威力或另一筆未減傷樣本也不足以保證同次事件的隨機值、屬性與條件相同。 例如假設只有最終下整，floor(D0 × 0.9)=90 同時容許整數 D0=100 與 101； 直接相除的 100 只是模型值。未核實取整位置與規則前不得宣稱精確原傷或任意設 ±1 為通過容差。

對已驗證採「減傷後扣盾」的普通、獨立傷害事件，再定義：

text
A = 此次實際吸收量（不是盾容量）
U = D - A                    # 扣盾後、尚未以 HP 裁切的傷害
L = min(U, H)                # H 為結算前 HP；限無其他 HP 變化的普通傷害
O = max(U - H, 0)            # overkill
D = A + L + O
D0 = M + A + L + O

damage-before-shield 指 D，不指 L。若已配對且欄位語意驗證成功，API 的 amount + absorbed + overkill 可作為候選 D（無 overkill 的明確 null 按其契約視為 0； 欄位缺失不可補 0）。此等式仍須對 FFXIV 實例驗證，並排除重複 calculation／resolution 計數。 HP 快照差是觀測值，遇同 frame 傷害、治療、自然回血、最大 HP 改變或防死時不等於 L。 只有 L 時不能反推 D；只有 D 時也不能假設差額全是盾。

M 計算的是完整傷害數值的減免，未裁切過量傷害，不是救回的有效 HP，也不承諾等同 FFLogs Healing credit。沒有明確平台規則前不把 M 加進 HPS。免疫造成 q=0 時不可除以 0： 即使觀測傷害為 0，原傷與免疫量通常仍未知；防死／傷害轉移另列模型，不以盾或百分比減傷解釋。

撤回 a_i = D0 × r_i。 原傷 100、兩項 10% 減傷：D=81、M=19，舊分配卻是 10+10=20。獨立「移除一項」的邊際量也不能直接相加當總量。

log-weight：a_i = M × log(1-r_i) / log(q)9.5、9.5約 8.980389、19.019611否；rDPS 來源只證明增傷用法
順序邊際：依順序逐次扣減，a_i = D0 × r_i × product(前項倍率)10、9（反序為 9、10）10、18（反序為 8、20）否；任意 log 順序不能充當遊戲優先順序
平均所有排列的邊際量（Shapley 候選）9.5、9.59、19否；順序無關、守恆，但需固定何者算一個貢獻者

各候選皆是從本節乘法模型推導的分帳方法，數學守恆不等於平台正確性。本階段不選 runtime 策略。 q=1 且資料完整時 M=0，所有份額為 0，避開 0/0；缺 metadata 不等於零減傷。 易傷倍率不得當成負的 r_i 混入分攤；其效果固定於基準並另記，無法固定則未知。 先以狀態實例計算，再依已確認 owner 加總，避免同一玩家的多技能被提前合併而改變權重。

未來若需整數輸出，保留高精度模型值並公開取整方法；可測候選是對已確認整數總量取各份額下整， 餘額按小數部分由大到小分配，同分依穩定事件／狀態 ID 排序。這是本地候選，非遊戲或 FFLogs 規則。 未知 owner 的份額保留為未歸因，不轉送其餘玩家；分攤規則尚未選定時整筆 M 保留未歸因。

text
sum(已歸因減傷) + 未歸因減傷 = 已知 M
sum(已歸因吸收) + 未歸因吸收 = 已知 A

若連總量都未知，保存 unknown 與原因，不用 0、總表差額或未耗盾容量填補；彙總必須另列未知事件數， 不能把已知子集合的加總標成完整總量。減傷／吸收各自守恆，不能互相補差。

可重現數學驗證與整合門檻 ​

在專案根目錄執行下列 Python 3 程式。它只驗證候選模型、守恆與不可識別的反例， 不匯入 parser，不測 runtime 的 unknown handling；後者必須等未來實作補 fixtures。

python
# mitigation-spec-math
from fractions import Fraction as Q
from itertools import permutations
from math import log, isclose

def product(xs):
    result = Q(1)
    for x in xs:
        result *= x
    return result

def model(d0, rates, shield=0, hp=1000):
    d0, shield, hp = map(Q, (d0, shield, hp))
    d = d0 * product(1-r for r in rates)
    m, a = d0-d, min(d, shield)
    loss, overkill = min(d-a, hp), max(d-a-hp, 0)
    assert d0 == m+a+loss+overkill
    return m, a, loss, overkill

r10, r20 = Q(1, 10), Q(1, 5)
# Z, R1-R3, S1-S4, O: (M, A, L, O)
vectors = [
    ([], 0, 1000, (0, 0, 100, 0)),
    ([r10], 0, 1000, (10, 0, 90, 0)),
    ([r10, r10], 0, 1000, (19, 0, 81, 0)),
    ([r10, r20], 0, 1000, (28, 0, 72, 0)),
    ([], 30, 1000, (0, 30, 70, 0)),
    ([], 50, 1000, (0, 50, 50, 0)),
    ([r10, r10], 30, 1000, (19, 30, 51, 0)),
    ([], 120, 1000, (0, 100, 0, 0)),
    ([r10, r10], 30, 40, (19, 30, 40, 11)),
]
for rates, shield, hp, expected in vectors:
    assert model(100, rates, shield, hp) == expected
assert 100*(r10+r10) == 20 != model(100, [r10, r10])[0]

def ordered(rates, order):
    remaining, parts = Q(100), [Q(0)]*len(rates)
    for i in order:
        parts[i] = remaining*rates[i]
        remaining -= parts[i]
    return parts

for rates in ([r10, r10], [r10, r20], [r10, r20, Q(3, 10)]):
    m = model(100, rates)[0]
    orders = list(permutations(range(len(rates))))
    marginal = [ordered(rates, order) for order in orders]
    linear = [m*r/sum(rates) for r in rates]
    shapley = [sum(p[i] for p in marginal)/len(orders) for i in range(len(rates))]
    q = product(1-r for r in rates)
    logarithmic = [float(m)*log(float(1-r))/log(float(q)) for r in rates]
    assert all(sum(p) == m for p in marginal)
    assert sum(linear) == sum(shapley) == m
    assert isclose(sum(logarithmic), float(m), abs_tol=1e-12)
    if rates == [r10, r20]:
        assert linear == [Q(28, 3), Q(56, 3)] and shapley == [9, 19]
    print('shares:', linear, shapley, logarithmic)

# S5: amount=0 / HP unchanged cannot distinguish 30 vs 60 fully absorbed.
assert model(30, [], 100)[2] == model(60, [], 100)[2] == 0
assert model(30, [], 100)[1] != model(60, [], 100)[1]
# B/X: the same D can have different D0 and mitigation totals.
assert 100*(1-r10) == 90 and model(90, [])[0] == 0
assert model(90, [r10])[0] == 9 and model(100, [r10, r10])[0] == 19
# Even a known final-floor rule can leave multiple integer original amounts.
assert int(100*(1-r10)) == int(101*(1-r10)) == 90
# T, N, F: type, death prevention, shared-frame accounting.
assert model(100, [Q(1, 20)])[0] == 5
assert min(100, 40-1) == 39 and 100-39 == 61
assert (50+50)-(100-20) == 20
print('PASS: 9 amount vectors, 3 allocation sets, ambiguity counterexamples')

每次已知 GCD 技能施放 → 視為一段 [施放時間, 施放時間 + recast] 的鎖定區間
GCD uptime% = 合併重疊區間後的總長度 / 戰鬥秒數

只有 ability metadata 收錄的 GCD 技能會納入（recast 預設 2.5s，部分技能有特別值），未知技能不硬算。

實作：pullSummary.ts 的 getGcdMetrics。

Evidence-based 進階分析 ​

進階分析只從實際封包與已解析的 Timeline 事件產生項目，每一項都保存規則版本、可信度、資料覆蓋率與可點擊的時間軸證據：

  • GCD 空窗：相鄰已知 GCD 間隔 - 該次已知 recast。未知技能或未知 recast 不預設為 2.5 秒；低於 1 秒不列 finding。
  • 副本目標狀態：只追蹤玩家 21 / 22 中帶 damage / miss effect、實際指向的 hostile actor，避免把對敵對 ID 寵物的治療誤當作可攻擊目標。ACT NetworkNameToggle (34) 的 01 從該時間起標為可選取，00 標為不可選取；狀態持續到下一個同 actor 標記、死亡／移除或 pull 結束。攻擊沉默、Boss 施法或 HP 更新都不會被反推成狀態切換。
  • 多人／多目標合併：同一時段只要一個已追蹤目標明確可選取，就標為 targetable；沒有可選取目標且所有 active targets 都明確不可選取，才標為 downtime；任何 active target 尚無標記，或當時沒有可證明的 active target，皆保留 unknown。
  • 有效空窗拆分：recast 後的時間依序扣除玩家死亡，再分成「可確認停手（downtime）」「Boss 狀態未知」「有效空窗（targetable）」；只把最後一項列為負向 finding。未知區間的秒數會顯示，但永遠不併入玩家失誤。
  • 證據與 coverage：34 標記會以 boss 類別寫入 Timeline，GCD finding 同時連結前後 GCD、死亡與可選取狀態事件。Encounter coverage 為 有明確 targetable/downtime 狀態的秒數 / pull 秒數；單項 coverage 則以該段玩家存活後的空窗為分母。
  • 職業規則邊界：通用 targetable interval 目前只替 GCD 空窗提供肯定證據；它不會直接把多目標 encounter 的每個 hostile actor 當成職業 DoT 的必須維持目標。明確 downtime 可用來排除連段／狀態的不可控區間，但未知 targetability 跨越的負向連段 finding 會降為 unknown。
  • 施法取消／中斷：直接配對 type 20 cast start 與 type 23 cancel；沒有成對證據時只留診斷，不產生肯定結論。
  • 冷卻間隔：只比較實際觀測到的使用時間與 metadata recast；不推定充能、資源、可攻擊時間或「少用幾次」。
  • 龍騎士規則：目前只在 ACT type 250 的 Game Version 精確符合 2026.07.22.0000.0000 時啟用，涵蓋 DoT 提前刷新／覆蓋、連段中斷、proc 消耗／覆蓋／到期與 buff window 內的 action sequence；不推定封包未提供的身位或量譜。

實作：targetability.ts、timeline/accumulator.ts、analysis/evidenceAnalysis.ts、analysis/core/、analysis/jobs/drg/；顯示與證據跳轉位於 web/components/analysis/AdvancedAnalysisPanel.vue。Advanced 頁面把唯一的共用「檢視對象」放在最前面，預設選取一位玩家，並同步控制角色重點、Pull 比較、分析發現與技能循環；UI 先呈現「下一把先看什麼」，再依規則類型分組，提供角色明細、整區、類型、單項與證據多層收合。Coverage 與 diagnostics 移到頁底並預設收合。低於 1 秒的 GCD 空窗不進入建議清單，避免一般封包抖動淹沒讀者。第一版 targetability 只證明「有可選取副本目標」，不代表站位、移動、資源或機制當下適合輸出。

同玩家／同副本 Pull 比較 ​

規則 same-player-same-encounter v1 只比較同一份來源檔中的頂層 Pull。必須同時滿足：

  • encounter identity 相同：優先用第一個 phase target name，沒有 phase 時才用 primary target name；名稱做 NFKC、空白與大小寫正規化，不用每把都會改變的 actor ID。
  • 玩家 ID、名稱、job ID 與 role 完全一致，兩場都有同口徑 player damage 與 Timeline。
  • 目前與候選 Pull 的邊界／結果 confidence 都不能是 low。

基準選擇先找 kill，同為成功 Pull 時依「玩家死亡較少 → DPS 較高 → GCD 使用率較高」排序。沒有成功 Pull 時，候選至少要滿足一項才算「較佳 Pull」：玩家死亡較少、DPS 高出 1% 以上，或 GCD 使用率高出至少 2 個百分點。沒有可比基準時，pullComparisons[].status 為 unavailable，並輸出 disabledReasons，不產生改善建議。

可比較時，每個有共同欄位的指標都輸出：

text
delta = currentValue - baselineValue
deltaPercent = delta / abs(baselineValue) × 100%  （baselineValue != 0 時）

第一版指標是 DPS、GCD 使用率、CPM、玩家死亡次數與有成對封包證據的施法取消／中斷次數；coverage.dimensions.comparison 以這五項為分母，只有目前與基準都有值的項目算 resolved。DPS 只呈現同玩家相對結果，不直接轉成改善指令，也沒有未知裝等下的絕對門檻。

nextPullFocus 只從目前比基準差且達最小差距的項目產生：死亡至少多 1 次、取消／中斷至少多 1 次、GCD 使用率至少少 2 個百分點、CPM 至少少 0.5。GCD 差異還必須在目前 Pull 找到 core.gcd-gap.actionable 的明確 targetable 證據；只有 unknown／excluded 空窗時不產生 GCD 改善項。先依可改善性，再依影響與差距排序，每位玩家最多三項；同一批 suggestion 也會加入既有 advancedAnalysis.items，沿用 rule/version、confidence、coverage 與 Timeline evidence 顯示。

限制：這是同一份 ACT log 經同一 parser 產生的個人相對比較，不校正裝等、隊伍組成、不同階段長度或隨機暴擊；它不是 FFLogs 排名，也不宣稱等同 FFLogs。整場 GCD 使用率與 CPM 沒有依可攻擊區間重新正規化，只用來定位值得回看的時間軸；GCD 改善 focus 另以明確 targetable 的有效空窗把關，仍不能單獨判定操作失誤。

實作：analysis/pullComparison.ts；資料型別在 shared/analysis.ts，顯示沿用 web/components/analysis/AdvancedAnalysisPanel.vue。

Advanced 角色職責摘要 ​

角色摘要是 web/analysis/advancedRoleViewModel.ts 產生的純顯示模型，不新增 parser 評分，也不參與 FFLogs／overlay 比較。它只重組同一份 PullSummary、Advanced rotation baseline、cast reconciliation、Timeline 與 metadata：

  • DPS：原始 GCD 節奏沿用 rotation baseline；「有效 GCD 空窗」只計所選玩家的 core.gcd-gap.actionable findings，unknown／excluded 長間隔只留作中性脈絡；爆發明細列出已辨識短效 buff 視窗的實際動作數與密度；目標傷害依所選玩家的 effective damage events 以 targetId 分組。
  • 坦克：只把 Timeline 中「來源為所選坦克」且 buffMetadata.kind = mitigation 的 status 視為減傷可觀測證據；同時間、同 ability 的多目標套用合併成一次，並保留可點擊的 Timeline event。承傷與 GCD 節奏只作回看上下文，不計算減傷成效或責任分數。
  • 治療：攻擊 GCD 必須同時是 cast reconciliation 已分類的 GCD，且同玩家、同時間、同 ability 有 effective damage event；GCD heal／oGCD heal 必須有 healingPotency 或 hotPotency metadata，再依 reconciliation 的 gcd／ability 分類。過量治療沿用 玩家 overheal / 玩家 raw healing。死亡前治療直接重用 death recap 的死亡前 15 秒事件，只列所選治療者對死者的已記錄治療。

角色摘要的 0 次只代表「目前資料與 metadata 沒有辨識到」，不等於沒施放。尤其減傷、治療分類、過量治療與死亡前治療都不能單獨證明漏減傷、缺治、過補或個人責任；Boss targetable window、未收錄技能、未消耗護盾與完整 encounter 分工仍不在這一版判定範圍。

小怪清理觀測 ​

web/analysis/addClearViewModel.ts 只讀既有 PullSummary.damageEvents、targetDamage.classification 與 Timeline，不新增 parser schema 或評分。只有分類為 add 且實際收到玩家有效傷害的目標會納入。

  • 有 W1-、W2- 等 encounter 標籤時依標籤分波；否則將首次受傷時間相隔不超過 8 秒的目標暫視為同一波，並明示為時間推定。
  • 波次起點是該波第一筆玩家有效傷害。所有已觀測 add 都有發生在首次受傷後的 Timeline death 時，清理時間 = 最後一隻 add 死亡時間 - 波次起點。
  • 任一目標缺 death 封包時不宣稱清完，只顯示 觀測區間 = 最後死亡或最後有效傷害時間 - 波次起點。
  • 玩家傷害占比為 玩家對該波 add 的有效傷害 / 全隊對該波 add 的有效傷害；首擊延遲為 玩家對該波首次有效傷害時間 - 波次起點。

限制：第一版尚未知道哪些 add 是必要、優先或可忽略目標，也沒有職業分工、控制、機制成功條件與跨 Pull 波次對齊。傷害占比和首擊延遲只作回看線索，不是玩家評分；DoT、寵物與 overkill 沿用既有 effective damage／owner 口徑。

威力估算 ​

威力（potency）來源 ​

  1. 優先用 XIVAPI action metadata 的 potency（含 description 解析）。
  2. 缺 metadata 的傷害事件，用同場次已知事件的比例推估：
damagePerPotency = 已知事件總傷害 / 已知事件總威力
推估威力 = 該事件傷害 / damagePerPotency

UI 進度條：深綠 = 直接 metadata、淺綠 = 傷害比例推估。

限制：buff 期間傷害偏高會讓推估威力略偏高；傷害為 0 的事件無法推估。

實作：analysis/rotationAnalyzer.ts 的 analyzePotency。

Buff 期間威力 / 覆蓋率 ​

Buff 期間威力 = 落在任一已收錄 buff 視窗內的事件威力總和
Buff 覆蓋率 = Buff 期間威力 / 總威力

buff 視窗只計已收錄的 raid buff / personal buff（3–45 秒的短效增益），排除坦姿、食物等長效狀態。

Pull 切分與階段 ​

Pull 切分 ​

三層 inactivity 門檻（預設 inactivityGapSeconds = 45 秒，可用 PULL_GAP_SECONDS 環境變數調整）：

滅團中（多數玩家死亡且未復活行動）→ min(inactivityGapSeconds, 20) 秒安靜就切
戰鬥中（主目標存活、未滅團）      → inactivityGapSeconds × 2（預設 90 秒，容許過場動畫）
其他                              → inactivityGapSeconds（預設 45 秒）

輔助規則：

  • 滅團偵測：玩家死亡（line 25，含環境殺 E0000000）加入死亡名單；之後施放技能（21/22）視為已復活移除。死亡中人數 ≥ max(4, 玩家數 × 0.75) 判定滅團。
  • 起點：非玩家來源對玩家的純治療（例如開戰前仙女的 仙光的擁抱）不會自行開啟 pull；pull 已開始時仍會進入治療統計。
  • 終點：主目標的 action HP snapshot 或 37 / 38 / 39 actor state 顯示 HP 歸零時立即結束；line 25 death 仍是備援。王死亡後的殘留 HoT、寵物治療不延長分母。
  • target swap 關閉：只有主目標「已死亡」後出現新的大血量目標才切新 pull；主目標活著時的新大目標視為同場戰鬥的階段角色或 add。
  • 主目標升級：血量 ≥ 現任主目標 1.2 倍的新形態會接手主目標身分（例如究極武器最終階段），pull 名稱才會對到玩家認知的 boss。

實作：pull/rules.ts、detectPulls.ts。

階段切分 ​

每個階段級目標（最大 HP ≥ 全隊最高玩家 HP × 6）「首次被玩家攻擊」記為一個階段起點
階段結束 = 下一個階段的開始（最後一段到 pull 結束）

只認玩家主動攻擊（21/22）——目標攻擊玩家不算接戰。同名目標重複出現（如亂流階段）不會切出新階段。階段使用 6 倍門檻以涵蓋血量低於 boss 候選（8 倍）的有效階段目標；主要目標、pull 切換與 kill 判定仍維持 8 倍門檻。

動物園的 羽環鰩（魚）與 賈巴沃克（馬）也是 encounter-specific 階段候選，不受 6 倍 HP 門檻限制，作為波次證據不足時的備援。這兩種目標的固定 HP 會在高血量隊伍中低於通用門檻。

每個階段產生完整報表（phaseReports[]）：所有表格從逐筆事件重算，與整場用同一套公式（DPS、rDPS*、Crit、治療、承傷、死亡、Casts、GCD uptime）。

階段報表的「目標敵人」會先把不同 actor ID 的同名目標合併，以同名目標的總傷害排序後最多顯示 8 種；避免大量同種 add 佔滿名額，隱藏其他實際受傷目標。

動物園目標（索取貓、羊、畝鼠、羽環鰩、賈巴沃克）會另以每隻 actor 首次參與玩家傷害互動的時間分波：相鄰首次活動相隔超過 15 秒就開始下一波。辨識到至少 3 種動物且 2–4 波時，每波最早活動時間會直接建立 W1-動物園至 W4-動物園 的 phase window，取代這些動物原本依 HP 產生的 generic markers。因此 W1 不會再被羊與畝鼠拆成兩段，W4 也不會混入 W3。

目標名稱顯示為 W1-畝鼠、W2-羽環鰩 等；同波同名的多隻 actor 仍合併傷害。動物園標籤依 W1–W4 排序並最多顯示 16 種，其他階段維持原本的 8 種上限。

左側導覽以 Pull → W1–W4 動物園 → 貓／羊／鼠／魚／馬 三層顯示。W 層保留整波時間窗的完整報表；動物層的總傷害、DPS、rDPS*、玩家傷害與技能傷害只納入對該動物的 damage events，分母仍是所屬 W 的完整長度。治療、護盾、承傷與死亡無法歸屬給單一敵方目標，因此維持該 W 的時間窗口徑。

限制：一般階段時間窗以「下一個 boss 首次被攻擊」為界，過場與中間 add 潮（亂流）會算在前一階段內。動物園若只留下單一波的傷害證據，或依 15 秒門檻分出超過機制的四波，無法建立 W1–W4 時間窗，會回退到 generic phase markers 與原始目標名稱。

實作：detectPulls.ts 的 trackPhaseMarker、pull/rules.ts 的 isPhaseTargetCandidate、pullSummary.ts 的 toPhaseReport、zoo.ts。

Kill / Wipe 判定 ​

kill：勝利系統訊息（寶箱出現）或 primary target 死亡
wipe：死亡玩家名數 ≥ max(4, 玩家數 × 0.75)
其餘：unknown

階段報表只有最後一個階段繼承整場結果（boss 在該階段倒下）。

實作：pullSummary.ts 的 inferResult。
